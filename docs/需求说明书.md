# EnterpriseMind V1 需求说明书（确认稿，摘要版）

## 1. 产品概述

EnterpriseMind 是面向单一企业私有化部署的通用企业知识库 Agent。系统以自然语言 Agent 作为统一入口，将企业非结构化文档与结构化业务数据库结合，通过 RAG、LLM Function Calling、LangGraph、Memory 和 Database MCP，为员工提供知识检索、问答、分析和受控操作能力。

V1 聚焦打通以下核心闭环：

1. 用户登录并通过 Agent 发起请求。
2. 上传、组织和管理企业文档。
3. 异步完成解析、OCR、图片理解、表格/代码提取、Chunk、Embedding 和索引。
4. 使用关键词与向量混合检索，经 RRF、Rerank 和阈值过滤生成上下文。
5. LLM 基于可靠上下文回答，并提供可定位、可高亮的引用。
6. Agent 在权限和安全约束下调用文档、知识库、Memory、RAG 和 Database MCP 等工具。

V1 不提供独立搜索入口；搜索、筛选、查询、分析和管理操作统一通过 Agent 完成，但保留知识库、文档、回收站、Memory 和管理后台等必要页面。

## 2. 用户、组织与权限

### 2.1 用户与登录

- 采用本地“用户名 + 密码”登录。
- 全新系统初始化时，必须根据部署配置和密码 Secret 自动创建首个启用管理员；初始化过程幂等，不设置默认账号或默认密码，也不得在重复启动时新增、覆盖或重置管理员。
- 用户状态为 `active` 或 `disabled`；停用后不可登录或使用 Agent，但历史会话和 Memory 保留。
- 系统支持多个管理员。
- V1 仅支持管理员重置用户密码，不提供普通用户自助修改、忘记密码、邮件找回或重置链接；重置后目标用户既有访问令牌立即失效。
- 普通用户只能属于一个部门。

### 2.2 部门

- V1 仅支持平级部门，不支持父子层级。
- 部门状态为 `active` 或 `disabled`。
- 仅当部门没有关联用户且没有关联知识库时才允许删除。

### 2.3 权限模型

V1 不实现复杂 ACL，权限由“系统角色 + 知识库类型 + 用户部门”确定：

- 管理员拥有所有知识库、文档、用户、部门和 Database MCP 配置的最高权限。
- 普通用户可访问企业公共知识库，以及所属部门的全部部门知识库。
- 普通用户可管理其有权访问知识库中的文档和文件夹。
- 普通用户不能创建、编辑、删除、恢复或迁移知识库。
- 文档和文件夹不设置独立权限，不支持跨部门分享。
- 所有服务端操作都必须执行最终权限校验，不能信任 LLM 生成的参数。

## 3. 知识库与文件组织

### 3.1 知识库

支持两类知识库：

- 企业公共知识库：所有有效用户均可访问。
- 部门知识库：绑定一个部门，该部门有效成员自动获得权限；一个部门可拥有多个知识库。

知识库仅维护名称、类型、描述和所属部门（部门知识库）。成员关系动态计算，不单独维护。管理员可迁移部门知识库；迁移后权限立即按新部门生效，既有文档、Chunk 和 Embedding 无需重新处理。

### 3.2 文件夹

- 知识库内支持多级文件夹，以及创建、重命名、移动、拖拽移动和删除。
- 文件夹用于组织文档、限制检索范围和辅助 Agent 定位，不参与权限计算。
- 删除非空文件夹需要二次确认，文件夹及其全部子项一并进入回收站。

## 4. 文档管理

### 4.1 支持格式

支持 PDF、DOC/DOCX、PPT/PPTX、XLS/XLSX、CSV、Markdown、TXT、PNG、JPG/JPEG 和 WEBP。

### 4.2 上传与元数据

- 支持页面单文件/批量上传，以及 Agent 自然语言上传。
- 每个文件创建独立异步处理任务。
- 用户可修改文档名称、描述和所属文件夹；名称、描述和路径参与检索。
- 文件类型、上传时间、上传人、MinIO Object Key、处理状态、Chunk 和 Embedding 等系统字段不可人工修改。

### 4.3 同名与覆盖

- 同一目录禁止完全同名文件，不同目录允许同名。
- 上传同名文件时询问是否覆盖；覆盖属于高风险操作，必须二次确认。
- 覆盖处理期间旧内容继续参与 RAG；新文件在完整处理成功，或达到可激活的 `partial_success` 条件后，原子切换为新内容。切换成功后旧内容退出 RAG，并异步清理旧解析、OCR、图片理解、表格、Chunk、Embedding 和搜索索引；新文件处理失败时继续使用旧内容。首次上传没有旧内容可回退。
- 不覆盖时，用户需修改名称后保存为独立文档。
- V1 不提供文档版本管理。

### 4.4 存储与预览

- 原始上传文件、Agent 生成文件、导出文件和图表文件存储于 MinIO。
- PostgreSQL 只保存文件元数据和 MinIO 对象引用。
- PDF、图片、Markdown 和 TXT 直接在线预览；Office 文件转换为 Web 友好格式后预览，原文件始终保留。

## 5. 文档解析与索引

### 5.1 处理流水线

文档上传后异步执行：

```text
保存原文件 → 结构解析 → 按需 OCR → 按需图片语义理解
→ 表格解析 → 代码块提取 → 结构化 Chunk → Embedding → 建立检索索引
```

### 5.2 解析要求

- OCR 仅用于扫描 PDF、图片型 PDF、图片或无法可靠提取文字的页面，并保存页码、Bounding Box 等原文位置映射。
- 架构图、流程图、图表、截图和 PPT 图片除 OCR 外还需调用 Vision API 生成可检索的语义描述。
- 表格需尽量保留表名、Sheet、表头、行列、单元格及原始位置，不能简单转为普通文本。
- 代码块独立存储语言、章节、父标题和原始位置；命中时自动补充前后解释文本。
- Chunk 采用结构优先切分，按标题、章节、段落、列表、表格、代码块、图片、Slide 和 Sheet 等结构划分；超长块再按可配置的最大长度与 overlap 二次切分。

### 5.3 状态、失败与重试

文档处理状态包括：`pending`、`processing`、`success`、`partial_success`、`failed` 和 `recycle_bin`。

- 仅成功处理的页面或 Chunk 可参与 RAG。
- `partial_success` 必须记录失败位置、阶段和原因，并允许只重试失败部分。
- 进度展示采用“当前阶段 + 阶段内部进度”，不计算统一总百分比。
- PostgreSQL 是任务状态的真实来源，WebSocket 只用于实时推送阶段、进度和结果。

## 6. RAG 与引用

### 6.1 检索范围

- 默认检索当前用户可访问的全部知识库。
- 用户明确指定部门、知识库、文件夹、格式等范围时，Agent 可进一步缩小范围。
- LLM 只能缩小范围，不能扩大用户权限。

### 6.2 混合检索流程

```text
问题理解 → 关键词检索 + 向量检索 → RRF 融合
→ Rerank → 相关性阈值过滤 → 相邻 Chunk 合并 → 去重
→ 最多 10 个上下文块 → LLM 回答
```

- 关键词检索负责编号、项目代号、接口名、文件名、型号和精确字段等召回；向量检索负责语义召回。
- 最终上下文不要求凑满 10 条；没有内容达到阈值时，必须明确说明知识库依据不足，不得以低质量材料强行作答。
- 候选数、RRF、Rerank 阈值、Chunk 长度与 overlap、最终上下文上限均通过配置文件管理。

### 6.3 引用与定位

所有基于企业知识库事实的回答必须附带来源，至少包含知识库、文档名称、页码/Slide/Sheet/段落和原文片段。引用应支持在线预览并定位原文：

- PDF 和图片：定位页或图片并高亮 Bounding Box。
- DOCX：定位标题或段落并尽量高亮。
- PPT：定位 Slide 和文本框/区域。
- Excel：定位 Sheet 和单元格/区域。
- Markdown/TXT：定位并高亮对应文本。

## 7. Agent 能力与执行模型

### 7.1 能力范围

Agent 支持知识问答、文档搜索与筛选、单/多文档总结对比、知识归纳、内容生成、翻译、数据库查询与分析、按需图表生成、文档/文件夹/知识库操作和 Memory 管理。

管理员权限内的知识库和系统操作也可通过 Agent 发起，但仍必须通过确定性后端完成鉴权、校验和执行。

### 7.2 架构职责

- LLM：理解意图、选择 Tool、生成 Function Calling 参数，并结合 Tool Result 继续推理。
- LangGraph：管理状态、条件流程、循环、Tool Guard、确认节点、次数限制、取消/恢复和 Checkpoint。
- 确定性后端：执行权限检查、参数校验、RAG、SQL 安全、数据库/MinIO 操作和各类 Tool。
- 所有 LLM 输出均按不可信输入处理。

### 7.3 Tool 与异常处理

内部 Tool 覆盖文档搜索和管理、文件夹管理、知识库管理、失败任务重试和 Memory 管理。单轮任务可组合 RAG、Database MCP 和其他 Tool：无依赖的调用并行执行，有依赖的调用串行执行。

- 临时失败可自动重试。
- 部分 Tool 最终失败时，允许基于成功结果继续回答，但必须指出失败数据源和结论局限。
- 问题完全依赖失败 Tool 时，明确告知当前无法完成，不得补造企业事实。
- 最大 Tool Call、最大 Replan 次数和单 Tool 最大 Retry 次数均可配置并分别计数。

### 7.4 交互与任务状态

- 最终回答通过 SSE/HTTP Streaming 流式输出。
- 前端展示“理解、检索、查询、合并、生成”等高层步骤，可展示并行任务，但不展示模型内部推理过程。
- 用户可停止任务，状态变为 `cancelled`；之后可基于 LangGraph Checkpoint 继续。
- Agent Run 状态统一为 `pending`、`running`、`waiting_confirmation`、`cancelled`、`completed` 和 `failed`。
- Checkpoint 存储于 PostgreSQL，只在关键节点保存；任务完成后删除中间 Checkpoint，仅保留最终状态。
- 恢复涉及实时业务数据的任务时，必须重新查询数据库。

## 8. 高风险操作与对象消歧

以下操作必须二次确认：

- 删除文档或知识库。
- 删除非空文件夹。
- 删除会话。
- 永久删除回收站内容。
- 覆盖同名文档。
- 将 Agent 生成内容正式写入知识库。

重命名、移动、恢复、上传和失败重试无需二次确认。

Agent 可按文件名、描述、路径和正文模糊定位对象；若存在多个高相关候选，必须列出候选让用户选择，尤其不能对删除、覆盖、移动和重命名等修改操作擅自选定对象。

## 9. 会话、上下文与 Memory

### 9.1 会话管理

支持新建、重命名、继续、查看历史和删除会话。删除会话需要二次确认，确认后永久删除且不进入回收站。

### 9.2 上下文管理

长会话上下文由当前输入、近期原文、较早会话摘要、长期 Memory 和当前 RAG/Tool 结果组成。达到 Token 阈值后，将较早消息压缩为摘要。

会话摘要和 Memory 不能作为企业事实的最终依据；涉及企业事实时必须重新通过 RAG 或 Database MCP 获取最新且经权限校验的数据。

### 9.3 长期 Memory

- 来源包括系统自动提取和用户主动要求记住，写入前统一经过 Memory Guard。
- 分类为 `preference`、`work_context`、`ongoing_context` 和 `other`。
- 主要保存用户偏好、长期工作上下文和持续任务上下文。
- 不保存密码、Token、API Key、高度敏感个人信息或企业敏感知识原文。
- 用户可查看、新增、修改和删除；新旧内容冲突时优先更新旧 Memory。

## 10. Database MCP

### 10.1 接入范围与权限

- V1 只接入一个 PostgreSQL 企业业务数据库；EnterpriseMind 自身 PostgreSQL 不通过 MCP 暴露。
- 业务数据库必须使用只读账号，仅允许 SELECT、Schema 和统计查询。
- 所有用户可使用 Database MCP，但只能访问“全局白名单 ∩ 当前用户部门权限”内的表或 View。
- 优先通过 View 暴露脱敏、裁剪并封装业务逻辑的数据。
- 只向 LLM 提供用户当前有权访问的 Schema，不泄露无权限表名、字段名或注释。

### 10.2 SQL 安全

```text
用户问题 → 读取 Schema 缓存 → LLM 生成 SQL
→ SQL Guard → Database MCP → 查询结果
```

SQL Guard 必须校验只读性、对象存在性、全局白名单、部门权限、返回行数和执行超时，禁止 INSERT、UPDATE、DELETE、DROP、ALTER 和 TRUNCATE 等写入或结构变更语句。

Schema 缓存包含表/字段名称、类型、主外键及注释；长期快照保存于 PostgreSQL，Redis 可用于热点缓存，管理员可手动刷新。

### 10.3 查询结果与连续追问

- 普通查询默认最多返回 100 行，超限时截断并返回 `has_more = true`，后续通过分页获取。
- 统计分析优先使用 COUNT、SUM、AVG、GROUP BY 等聚合 SQL，只将聚合结果交给 LLM。
- 大量完整数据通过 CSV/XLSX 导出，不进入 LLM Context。
- 连续追问保留上一轮语义，但每轮都基于当前问题、已有语义和当前可访问 Schema 重新生成 SQL 并重新经过 SQL Guard，不能直接修改旧 SQL 字符串。
- 关键查询条件有歧义时必须询问用户，不得猜测。

### 10.4 数据来源与可视化

数据库回答必须标注数据源、数据库、表/View、查询时间和查询条件或摘要。RAG 与数据库联合回答时，两类依据分别展示。

仅在用户明确要求时生成柱状图、折线图、饼图或表格。图表可导出为 PNG、PDF、XLSX 或 CSV，并保留数据来源、统计口径和查询时间。

## 11. 内容生成、导出、语言与翻译

- Agent 可基于企业资料生成总结、报告、检查清单、对比文档、说明文档和表格。
- 写入知识库的流程为：生成 → 用户预览 → 用户确认 → 保存文件 → 异步解析和索引 → 参与 RAG。该确认属于操作确认，不是审核流程。
- 生成内容可直接导出为 DOCX、PDF、Markdown 或 XLSX，并保留引用；导出文件默认不进入知识库。
- 支持中文、英文和中英文混合检索，以及中英互译、文档/指定章节翻译和翻译后总结。
- Embedding 模型需支持多语言，翻译结果需保留与原始来源的关系。

## 12. 回收站与数据清理

- 文档、文件夹和知识库删除后进入回收站，保留 30 天。
- 进入回收站后立即停止正常访问和参与 RAG。
- 30 天内允许恢复；到期后自动永久删除。
- 永久删除需清理业务记录、MinIO 文件、解析/OCR/Vision/表格结果、Chunk、Embedding 和检索索引。
- 用户主动永久删除回收站内容时必须二次确认。

## 13. 模型服务与可靠性

EnterpriseMind 不部署模型，统一通过 Provider 接口调用外部 LLM、Embedding、Rerank、Vision 和 OCR API，具体模型与服务地址通过配置文件指定。

- 所有模型调用支持超时和自动重试。
- 临时网络错误、超时和部分 5xx 最多重试 3 次。
- 鉴权失败、参数错误、模型不存在等不可恢复错误不重复重试。
- V1 不进行模型微调，优先依靠 Prompt、RAG、Embedding、Rerank、Tool Use、MCP 和 Memory 解决问题。

Prompt 集中存放于 `prompts/agent`、`prompts/rag`、`prompts/database`、`prompts/memory`、`prompts/vision` 和 `prompts/conversation` 等目录，由代码和 Git 管理；V1 不提供数据库化、在线管理、历史版本、回滚或 A/B Test。

## 14. 技术架构与部署

### 14.1 技术栈

- 前端：React + TypeScript。
- 后端：FastAPI；Pydantic 按实际需要使用。
- Agent 编排：LangGraph；LangChain 仅按需作为组件库，不采用其默认 Agent。
- PostgreSQL：业务数据、用户/会话、Memory、文档元数据、任务状态、Agent Run、Checkpoint 和 Schema 快照。
- pgvector：Embedding 和向量检索。
- Redis：异步任务队列和临时缓存。
- Worker：文档解析、OCR、Vision、表格、Chunk、Embedding 和索引。
- MinIO：原始文件、生成文件和导出文件。

### 14.2 部署形态

- Linux + Docker Compose，单企业私有化部署。
- 建议服务包括 `frontend`、`api`、`worker`、`postgresql`、`redis`、`minio` 和 `database-mcp-server`。
- 模型服务独立部署，通过 API 接入。

### 14.3 并发与扩展

V1 不设固定并发和 SLA，但架构需支持 FastAPI 异步请求、多个文档任务并发、PostgreSQL 连接池、Worker 横向扩展、SSE 流式回答和 WebSocket 状态推送，避免为极端并发过度设计。

## 15. 前端页面范围

V1 页面包括：

- 登录页。
- Agent 对话页。
- 知识库页。
- 文档与文件夹管理。
- 回收站。
- Memory 管理。
- 管理员页面：用户（含管理员重置密码）、部门、知识库和 Database MCP。

V1 不建设独立搜索页、首页仪表盘、通知中心、操作日志页、审核页、模型配置页和 Prompt 配置页。

V1 不建立持久化操作审计表或 SQL 审计记录；运行诊断使用脱敏的服务日志和指标。为回答引用、分页和状态恢复保存的业务状态不作为独立审计日志。

## 16. 测试、评测与 CI

### 16.1 Agent/RAG 评测

采用规则自动判断与人工查看结合，不使用 LLM-as-a-Judge。

- 自动评测：正确文档命中、引用、Tool 选择、SQL 只读、越权防护、二次确认、Rerank 等。
- 人工评测：回答清晰度、总结完整性、对比合理性和表达质量。

### 16.2 软件测试与 CI

- 建立单元测试、API 测试和关键流程集成测试。
- 重点覆盖权限、SQL Guard、RRF、Rerank、Chunk 合并、Memory Guard、状态流转、上传到 RAG、Agent Tool/MCP 调用、RAG 与 Database MCP 及其他 Tool 的组合任务，以及删除确认和回收站。
- 个人开发直接使用 `main` 分支，本地测试后提交并推送。
- GitHub Actions 执行前端类型检查/Lint、后端 Ruff、pytest 和适合 CI 的测试；V1 不做自动 CD。

## 17. V1 明确不包含

- SaaS、多租户、多业务数据库。
- LDAP、AD、SSO、MFA、验证码和复杂账号安全策略。
- 复杂/个人/文档级 ACL、跨部门分享、数据库列级或行级权限。
- 审核流程、文档版本、评论批注、在线 Office 正文编辑。
- 复杂部门层级、文档标签、知识库/文档停用。
- 独立搜索、首页仪表盘、通知中心和操作审计日志。
- 模型配置后台、Prompt 在线管理/历史/回滚/A-B Test、模型微调。
- 数据库写操作、复杂 BI 图表和自动 CD。

## 18. V1 关键验收原则

1. 任意检索和操作均不能突破角色、知识库类型、部门或数据库白名单权限。
2. 知识库事实回答有足够依据时必须引用并可定位；依据不足时明确拒绝推断。
3. 文档从上传到解析、检索、引用和回收站的数据状态完整一致，可追踪并可恢复失败部分。
4. Database MCP 全链路只读，Schema 暴露和 SQL 执行均经过权限与安全校验。
5. 高风险操作必经确认，模糊对象必经用户选择，LLM 不直接执行可信操作。
6. Agent 能组合 RAG、数据库和内部 Tool，并在部分失败时准确表达结论边界。
7. 长会话与 Memory 可持续使用，但企业事实始终重新从受控数据源获取。
8. 核心服务可通过 Docker Compose 在企业 Linux 环境完成私有化部署。
