# EnterpriseMind V1 检索增强生成参数与离线评测方案（确认稿）

## 1. 文档目的

本文档确定 EnterpriseMind V1 检索增强生成（RAG）的首版可执行参数基线、检索降级规则和离线评测门槛。

本设计直接复用：

- 《需求说明书》的关键词与向量混合检索、RRF、Rerank、阈值过滤、相邻 Chunk 合并、去重和最多 10 个上下文要求。
- 《文档处理状态机与任务协议》的活跃代次和 `partial_success` 语义。
- 《内容分块、来源锚点与索引结构设计》的 Chunk、锚点、关键词、向量与权限过滤约束。

本阶段不新增独立搜索入口、业务表、在线参数后台、查询历史或审计记录。模型相关阈值必须在具体 Provider 和模型确定后通过本方案校准，不能伪造跨模型通用分数。

## 2. 检索流程

V1 固定使用以下顺序：

```text
问题规范化与检索范围收缩
→ 计算当前用户可访问知识库
→ 内容关键词、文档元数据和向量并行召回
→ 加权 RRF 融合与去重
→ Rerank
→ 模型相关阈值过滤
→ 受控相邻 Chunk 合并
→ Token 预算裁剪
→ 最多 10 个上下文块
→ LLM 回答并绑定实际来源锚点
```

任何阶段都不能扩大用户权限。LLM 只能提出知识库、文件夹、文档或格式等缩小范围，最终范围由服务端重新解析并鉴权。

## 3. 首版参数基线

### 3.1 参数状态

参数分为三类：

| 类型 | 含义 |
|---|---|
| 固定语义 | 为满足需求和安全约束必须保持，例如最多 10 个上下文 |
| 首版基线 | 可以直接作为首轮实现值，但上线前必须通过离线评测 |
| 模型校准值 | 只有选定具体模型后才能确定，不提供伪默认值 |

实施时这些键统一放入 Git 管理的 `config/rag.yaml`，环境变量只允许覆盖部署差异值。Secret、Provider 凭据和企业数据不得写入该文件；V1 不把参数复制到数据库或提供在线修改入口。

### 3.2 Chunk 参数

| 配置键 | 首版值 | 类型 | 说明 |
|---|---:|---|---|
| `rag.chunk.target_tokens` | `400` | 首版基线 | 普通结构块的目标长度 |
| `rag.chunk.max_tokens` | `600` | 首版基线 | 超过后执行结构内二次切分 |
| `rag.chunk.min_tokens` | `80` | 首版基线 | 同结构下短相邻文本可合并；不可拆结构允许更短 |
| `rag.chunk.overlap_tokens` | `80` | 首版基线 | 只用于同一超长结构块的相邻子块 |

约束：

- `0 <= overlap_tokens < max_tokens`。
- 表格、代码、图片和标题边界优先于 Token 数值，不能为凑长度破坏结构。
- Token 计数器必须由选定模型适配器明确提供；Provider 未提供兼容计数器时，必须选用经过该模型样本验证的确定性计数器。
- 修改 Chunk 参数只影响新处理代次；V1 不提供用户触发的全库在线重切分。

### 3.3 召回、融合与上下文参数

| 配置键 | 首版值 | 类型 | 说明 |
|---|---:|---|---|
| `rag.keyword.content_limit` | `50` | 首版基线 | Chunk 全文检索候选数 |
| `rag.keyword.metadata_document_limit` | `10` | 首版基线 | 名称、描述、路径命中文档数 |
| `rag.keyword.metadata_chunks_per_document` | `2` | 首版基线 | 每个元数据命中文档最多映射的 Chunk 数 |
| `rag.keyword.trigram_threshold` | `0.30` | 首版基线 | 文档和路径模糊匹配起点 |
| `rag.vector.candidate_limit` | `50` | 首版基线 | 向量候选数 |
| `rag.vector.exact_scan_max_chunks` | `5000` | 首版基线 | 授权候选不超过该值时优先精确排序 |
| `rag.rrf.k` | `60` | 首版基线 | RRF 排名平滑常量 |
| `rag.rrf.keyword_weight` | `1.0` | 首版基线 | 内容关键词排名权重 |
| `rag.rrf.vector_weight` | `1.0` | 首版基线 | 向量排名权重 |
| `rag.rrf.metadata_weight` | `0.5` | 首版基线 | 关键词通道内元数据分支权重 |
| `rag.rrf.fused_limit` | `30` | 首版基线 | 进入 Rerank 前的融合候选上限 |
| `rag.rerank.candidate_limit` | `30` | 首版基线 | Rerank 输入上限，不得大于融合上限 |
| `rag.rerank.min_score` | 无通用默认值 | 模型校准值 | 按实际 Rerank 模型离线校准 |
| `rag.context.max_blocks` | `10` | 固定语义 | 最终上下文块上限 |
| `rag.context.max_token_ratio` | `0.35` | 首版基线 | 最多占可用模型上下文窗口的比例 |
| `rag.context.absolute_max_tokens` | `6000` | 首版基线 | 上下文绝对上限 |
| `rag.context.neighbor_each_side` | `1` | 首版基线 | 每个种子 Chunk 每侧最多扩展一个关联邻块 |
| `rag.dedup.anchor_overlap_ratio` | `0.80` | 首版基线 | 锚点覆盖高度重合时保留更高分结果 |
| `rag.fallback.consensus_rank` | `20` | 首版基线 | Rerank 失败时判定双通道强证据的名次上限 |

最终检索上下文预算为：

```text
min(
  rag.context.absolute_max_tokens,
  floor(模型可用输入窗口 × rag.context.max_token_ratio)
)
```

“模型可用输入窗口”必须先扣除系统 Prompt、Tool Schema、当前问题、近期会话、会话摘要、Memory 和预留输出 Token，不能直接使用模型宣称的完整上下文窗口。

### 3.4 HNSW 参数

| 配置键 | 首版值 | 类型 | 说明 |
|---|---:|---|---|
| `rag.vector.distance` | `cosine` | 首版基线 | 使用 `vector_cosine_ops` 和 `<=>` |
| `rag.hnsw.m` | `16` | 首版基线 | 每层最大连接数 |
| `rag.hnsw.ef_construction` | `64` | 首版基线 | 构建期候选规模 |
| `rag.hnsw.ef_search` | `100` | 首版基线 | 高于官方默认 40 的首轮检索值 |
| `rag.hnsw.iterative_scan` | `strict_order` | 首版基线 | 过滤后继续扫描并保持严格距离顺序 |
| `rag.hnsw.max_scan_tuples` | `20000` | 首版基线 | 迭代扫描安全上限 |
| `rag.hnsw.scan_mem_multiplier` | `1` | 首版基线 | 首版保持官方默认内存倍数 |

`m = 16`、`ef_construction = 64`、默认 `ef_search = 40`、迭代扫描及 `max_scan_tuples = 20000` 均来自 pgvector 官方说明。本方案把查询期 `ef_search` 的起点设为 100，但必须与精确检索结果比较后决定是否保留。

所有查询期 HNSW 参数使用事务内 `SET LOCAL`，不能修改全局数据库默认值。构建参数变化需要重建对应模型索引，不能在请求中动态修改。

## 4. 问题规范化与范围收缩

### 4.1 问题文本

- 保存并传递给回答模型的是用户原始问题。
- 关键词查询使用与 `search_tokens` 相同的 NFKC、空白规范化、大小写折叠、中文分词和标识符拆分规则。
- 向量查询使用去除纯交互套话后的语义问题，但不能删除型号、编号、否定词、时间、版本和限定条件。
- 不通过 LLM 把问题改写成与原意不同的“更容易检索”问题。

### 4.2 范围优先级

服务端按以下顺序求交集：

```text
用户当前可访问知识库
∩ 用户明确指定范围
∩ Agent 解析出的缩小范围
∩ 当前未进回收站且存在活跃可检索代次的文档
```

- 用户明确指定文档时，不能因为其他文档分数更高而扩大到未指定文档。
- 范围不存在、已删除或无权限时，按不可枚举资源规则处理。
- 文件格式、文件夹和文档名称存在多个高相关候选时，修改操作必须消歧；纯问答可以在授权候选范围内检索并展示实际来源。

## 5. 关键词召回

### 5.1 内容关键词分支

- 使用预处理后的查询词构建 `simple` 配置的 `tsquery`。
- 使用 `chunks.search_vector @@ query` 召回，原始分值采用 PostgreSQL `ts_rank_cd`。
- 在 `LIMIT 50` 前完成权限、回收站、`active_revision_id`、代次状态和 `chunks.status = ready` 过滤。
- 编号、型号、接口名、项目代号、代码标识符和精确字段优先保留完整词项。

### 5.2 文档元数据分支

- 对当前授权范围内的文档名称、描述和实时文件夹路径使用 `pg_trgm` 模糊匹配。
- 元数据分支最多返回 10 个文档，每个文档最多映射 2 个当前活跃 `ready` Chunk。
- 文档内已有内容关键词命中时优先映射其最高排名 Chunk；没有内容命中时，按来源锚点顺序选择开头的可检索 Chunk。
- 元数据候选仍归入关键词通道，不构成第三种用户可见检索方式。

### 5.3 关键词内部排名

内容关键词和元数据分支不直接混合不可比原始分数，而是作为两个排名列表进入统一加权 RRF：内容列表权重 `1.0`，元数据列表权重 `0.5`。

## 6. 向量召回

### 6.1 查询向量

- 使用当前 active Embedding 模型生成一个查询向量。
- 查询向量维度必须与 active 模型索引维度一致。
- 空向量、零向量、非有限数值或维度不一致时拒绝进入向量查询。
- 查询向量只在当前请求内使用，不持久化。

### 6.2 精确与近似路径

1. 先计算当前授权且活跃的 `ready` Chunk 数量。
2. 数量不超过 `5000` 时，通过合法 `chunk_id` 集合执行精确余弦距离排序。
3. 数量超过 `5000` 时，使用当前模型 HNSW 表达式部分索引和严格顺序迭代扫描。
4. HNSW 查询必须把授权和活跃条件放在同一 SQL 查询中；若 `EXPLAIN` 或运行时结果表明过滤后无法补足候选，自动回退精确路径。

不能先取全库固定 Top-K，再在应用层删除无权限内容。

### 6.3 近似召回验收

对同一查询和授权范围，以精确余弦 Top-50 为真值，计算 HNSW Recall@50。HNSW 的速度优势不能抵消权限错误或不可接受的召回损失。

## 7. 加权 RRF 融合

### 7.1 公式

排名从 1 开始。候选 Chunk 的融合分数为：

```text
RRF(chunk) = Σ weight(channel) / (k + rank(channel, chunk))
```

缺失于某个列表的 Chunk 在该列表贡献为 0。V1 输入列表和权重为：

| 排名列表 | 权重 |
|---|---:|
| 内容关键词 | `1.0` |
| 文档元数据 | `0.5` |
| 向量 | `1.0` |

RRF 只使用名次，不对 `ts_rank_cd`、trigram 相似度和余弦距离做查询内 min-max 归一化。这样可避免分值尺度不同和单次候选分布改变融合语义。

RRF 是将多个检索系统排名进行融合的经典方法；首版 `k = 60` 是待领域数据验证的基线，不是不可修改常量。

### 7.2 去重与截断

- 同一 `chunk_id` 只保留一条融合记录，并保留各列表原始排名和分值。
- 同文档、同代次、同来源单元内，两个 Chunk 的相同锚点或规范化 `quote_text` 覆盖短者达到 `0.80` 时视为高度重合，保留 RRF 分数更高者；分数相同时保留 Token 更少者。不同文档或代次不能仅因文字相似而去重。
- 去重后按 RRF 分数降序、最佳单通道名次升序、`chunk_id` 升序稳定排序。
- 只把前 30 个候选送入 Rerank。

## 8. Rerank 与阈值

### 8.1 Provider 适配要求

- Rerank Provider 必须返回每个候选的稳定相关性分数和顺序。
- Adapter 必须明确分数方向、范围和版本，不能假设所有 Provider 都使用 `0..1`。
- 不使用当前查询候选的 min-max 结果作为阈值依据。
- `rag.rerank.min_score` 按具体模型、语言和企业数据校准，并与 `model_key` 配套配置。
- 模型切换或版本变化必须重新执行阈值校准。

### 8.2 阈值过滤

- Rerank 后先删除低于已校准阈值的候选，再执行相邻扩展。
- 最终不要求凑满 10 个上下文块。
- 没有候选通过阈值时，返回“当前知识库依据不足”的结果，不能降低阈值强行回答。
- 只有一个候选通过时可以回答，但该候选仍必须具备有效锚点并足以支撑结论。

### 8.3 Rerank 输入

Rerank 输入仅包含原始问题、Chunk 内容和必要结构上下文，不包含用户身份、部门、权限列表、数据库 ID、MinIO 地址或其他候选的敏感信息。

候选超过 Provider 单项长度限制时，按锚点边界裁剪，并优先保留关键词命中片段、标题路径和主要正文；不能在无法定位的中间位置随意截断后生成引用。

## 9. 相邻合并、去重与上下文预算

### 9.1 相邻扩展

每个通过阈值的种子 Chunk 每侧最多扩展 1 个 Chunk，并且必须同时满足：

- 属于同一文档和同一活跃代次。
- 状态为 `ready`。
- 当前用户仍有权限。
- `context_group` 相同，或锚点证明为同一结构的直接相邻部分。
- 合并后不超过单块和总上下文 Token 预算。

代码与解释、表格连续行组、超长段落子块、图片与 Caption 可以扩展；仅因数据库 `ordinal` 相邻不能自动合并。

### 9.2 合并顺序

1. 按 Rerank 分数依次选择种子 Chunk。
2. 对每个种子执行受控邻块扩展。
3. 按来源锚点的原文顺序排列合并内容。
4. 再次执行 Chunk ID 和锚点覆盖去重。
5. 在总 Token 预算内保留最多 10 个上下文块。

一个合并上下文块计为一个 `max_blocks` 单位，但内部所有被实际采用的 Chunk 和锚点必须继续可追踪。

### 9.3 预算不足

- 优先保留 Rerank 分数高且能独立支撑问题的种子 Chunk。
- 邻块先于种子块被裁剪。
- 不能从表格中只保留值而丢弃必要表头，也不能从代码中只保留局部语句而丢失必要定义。
- 上下文被预算截断时不改变引用锚点的实际范围。

## 10. 失败与降级

| 失败点 | 降级规则 | 用户结果 |
|---|---|---|
| 查询 Embedding 失败 | 使用关键词列表继续，RRF 只计算可用列表 | 明确说明语义检索暂不可用；依据不足则不回答 |
| PostgreSQL 关键词召回失败 | 使用向量列表继续 | 明确说明精确关键词检索暂不可用；依据不足则不回答 |
| 一个召回分支为空 | 使用其他正常分支 | 不把“无命中”误报为系统错误 |
| Rerank 最终失败 | 仅在存在强证据时使用 RRF 结果 | 明确说明相关性复核暂不可用 |
| 两类召回均失败 | 不生成知识库事实回答 | 返回当前无法检索企业资料 |
| 所有候选低于阈值 | 不降阈值 | 返回知识库依据不足 |

Rerank 失败时的“强证据”只允许：

- 精确文档名、路径、编号或代码标识符命中，并有直接内容支持；或
- 同一 Chunk 同时进入内容关键词和向量列表的 `rag.fallback.consensus_rank` 名次以内。

除此之外不得用未经过 Rerank 的单通道弱相关结果生成企业事实。

临时网络错误、超时和部分 5xx 仍按统一模型调用策略最多自动重试 3 次；鉴权、参数和模型不存在错误不重复重试。

## 11. 离线评测数据集

### 11.1 首版规模

首版最少 200 个评测问题：

| 切片 | 数量 | 重点 |
|---|---:|---|
| 精确编号、型号、接口名和项目代号 | 25 | 关键词召回 |
| 语义改写与自然语言问法 | 25 | 向量召回 |
| 中文、英文和中英混合 | 15 | 多语言 Embedding 与分词 |
| 表格和数值定位 | 15 | 表头、行列和单元格锚点 |
| 代码与接口说明 | 10 | 标识符、语言和解释邻块 |
| OCR、图片和图表 | 10 | OCR/Vision 与区域引用 |
| 多文档总结或对比 | 10 | 多来源覆盖 |
| 指定知识库、文件夹或文档范围 | 10 | 范围收缩 |
| 无依据、错误前提和知识库外问题 | 30 | 阈值与拒答 |
| 普通用户权限、部门隔离和管理员范围 | 30 | 零越权 |
| 覆盖、`partial_success`、回收站和恢复 | 20 | 活跃代次与生命周期 |
| **合计** | **200** |  |

### 11.2 标注内容

每个评测问题至少包含：

- 问题文本和语言。
- 执行用户或角色、部门及允许范围。
- 是否预期无答案。
- 相关文档、Chunk 和来源锚点。
- 相关性等级：`2 = 直接充分`、`1 = 有帮助但不充分`、`0 = 不相关`。
- 必须出现的关键事实或数值。
- 允许的等价引用范围。
- 用例切片标签。

评测集是人工整理的开发数据，不从生产用户查询日志自动采集。包含企业敏感内容的完整评测集只保存在受控环境，不写入公开仓库、运行日志或指标。

### 11.3 数据划分

- 校准集 120 条，用于参数搜索和 Rerank 阈值校准。
- 验证集 40 条，用于选择最终参数组合。
- 冻结测试集 40 条，只用于发布前验收。
- 同一文档、同一模板派生文档和近重复问题必须位于同一划分，避免内容泄漏。

CI 使用不含企业敏感内容的最小回归子集；完整 200 条评测在受控环境执行。

## 12. 自动评测指标

### 12.1 检索指标

| 指标 | 计算范围 | 首版门槛 |
|---|---|---:|
| 内容关键词 Recall@50 | 对应切片 | `>= 0.90` |
| 向量精确 Recall@50 | 语义与多语言切片 | `>= 0.90` |
| HNSW 对精确结果 Recall@50 | 全部正向问题 | `>= 0.95` |
| RRF Recall@30 | 全部正向问题 | `>= 0.90` |
| Rerank nDCG@10 | 全部正向问题 | `>= 0.85` |
| 精确标识符 MRR@10 | 编号、型号、接口和代码切片 | `>= 0.95` |
| 最终上下文证据覆盖率 | 全部正向问题 | `>= 0.90` |

nDCG 用于利用 `0/1/2` 分级相关性评估排序质量，MRR 用于衡量第一个直接相关结果的位置。

除整体门槛外，任一关键切片的 RRF Recall@30 不得低于 `0.80`。Rerank 后任一关键切片的 nDCG@10 相对 RRF 前不得下降超过 `0.02`。

### 12.2 安全与引用指标

| 指标 | 首版门槛 |
|---|---:|
| 无权限 Chunk 返回率 | `0` |
| 非活跃代次或回收站 Chunk 返回率 | `0` |
| 知识库引用创建时 Chunk—锚点有效率 | `100%` |
| 引用与当前授权来源一致率 | `100%` |
| PDF/PPT/XLSX/图片/文本结构定位成功率 | `>= 99%` |
| DOCX 段落定位成功率 | `100%` |
| DOCX 精确字符高亮成功率 | `>= 95%` |
| 无依据问题正确拒答率 | `>= 95%` |

任何权限泄漏、旧代次泄漏或引用指向其他文档代次都直接判定版本不通过，不能用平均分抵消。

### 12.3 性能记录

需求未设置固定 SLA，因此首版只记录并比较：

- 关键词、查询 Embedding、向量、RRF、Rerank 和总检索的 P50/P95。
- HNSW 扫描元组数、是否触发精确回退。
- 候选数、最终块数和上下文 Token 数。
- 索引大小和构建时间。

性能结果使用脱敏聚合值，不记录用户原始问题、Chunk 正文或查询向量。正式 SLA 必须基于目标部署硬件实测后单独确认。

## 13. 人工评测

需求明确不使用 LLM-as-a-Judge。人工评测只检查：

- 回答是否被引用内容直接支持。
- 是否遗漏关键条件、限制或反例。
- 多文档总结和对比是否覆盖必要来源。
- 表格、代码、OCR 和 Vision 内容是否被正确解释。
- 依据不足时是否明确拒绝推断。
- 引用名称、页/Slide/Sheet/段落、原文片段和高亮是否可用。
- 降级回答是否准确说明缺失检索能力和结论局限。

每个用例记录“通过/不通过”和简短原因，不让人工评分替代可自动验证的权限、召回和定位指标。

## 14. 参数选择流程

### 14.1 基线建立

1. 固定评测语料、活跃代次、用户权限和模型版本。
2. 分别运行关键词、精确向量、HNSW、RRF、Rerank 和最终上下文结果。
3. 先保证权限、代次和引用指标全部通过，再比较召回和排序。
4. 使用校准集搜索参数，使用验证集选择最简单且满足门槛的组合。
5. 冻结参数后只运行一次测试集；未通过时回到校准阶段，不能针对测试问题逐项调参。

### 14.2 调参顺序

按以下顺序调整，避免多组参数同时变化而无法解释：

1. Chunk 长度和 overlap。
2. 关键词规范化、trigram 阈值和候选数。
3. 精确/HNSW 切换阈值、`ef_search` 和扫描上限。
4. 各列表候选数、RRF `k` 和权重。
5. Rerank 输入数和模型相关阈值。
6. 相邻扩展、去重和上下文预算。

只有当前步骤达到指标后才进入下一步。

### 14.3 发布准入

发布配置必须同时满足：

- 所有零容忍安全和生命周期指标为 0 违规。
- 所有知识库引用可验证且可定位。
- 整体和关键切片达到检索门槛。
- 模型相关 Rerank 阈值已经完成校准。
- HNSW 查询计划和精确回退路径均通过实际 PostgreSQL 数据验证。
- 人工评测没有发现无依据企业事实。

参数配置和聚合评测报告由 Git 管理；不把评测过程建设成在线实验、A/B Test 或数据库历史系统。

## 15. 必须通过的场景

| 场景 | 验收结果 |
|---|---|
| 查询精确型号 | 关键词结果优先且引用准确 |
| 同义改写 | 向量召回能够补足关键词遗漏 |
| 中英混合问题 | 两种召回均使用一致范围和多语言模型 |
| 文件名命中但正文未命中 | 元数据分支映射少量活跃 Chunk，不加载整篇文档 |
| 用户明确指定单文档 | 召回范围不扩展到其他文档 |
| 普通用户库外高相似内容 | 结果中完全不存在无权限 Chunk |
| 覆盖处理中 | 只检索旧活跃代次 |
| 覆盖成功提交后 | 同一查询立即只检索新活跃代次 |
| 活跃 `partial_success` 补建中 | `pending` Chunk 不进入任一召回分支 |
| 回收站文档高相似 | 不进入候选集 |
| HNSW 过滤后候选不足 | 迭代扫描补足或精确回退 |
| Rerank 无候选过阈值 | 明确知识库依据不足 |
| Rerank 服务失败 | 仅强证据允许降级回答，并明确局限 |
| 相邻代码解释 | 仅同 `context_group` 的直接邻块被合并 |
| 最终上下文超预算 | 保留高分种子和结构完整性，不强行凑满 10 块 |
| 无依据问题 | 拒绝推断企业事实 |

## 16. 明确不增加的能力

本方案不增加：

- 用户可见的 RAG 参数调节页面。
- 在线 A/B Test、用户行为追踪或点击反馈训练。
- 生产查询、向量、候选内容或完整回答的评测日志。
- LLM-as-a-Judge。
- 为提高召回而放宽权限、回收站或活跃代次过滤。
- 无阈值的“始终返回若干结果”模式。
- 多套 Embedding 模型同时参与线上召回。

## 18. 后续设计输入

本方案已与《智能体编排状态与检查点设计》（确认稿）对齐，并共同复用：

- 检索范围只能缩小、不能扩大权限的规则。
- 关键词、向量、RRF、Rerank、阈值和上下文构建的确定性服务边界。
- 各检索分支失败时的降级和终止条件。
- 最终上下文及来源锚点作为 Agent 回答输入，不由 LLM 自行构造来源。
- 最大 Tool Call、最大 Replan 和单 Tool Retry 分别计数的既有需求。
