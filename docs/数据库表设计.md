# EnterpriseMind V1 数据库表设计（确认稿）

## 1. 文档定位

本文档依据《EnterpriseMind V1 需求说明书》和《EnterpriseMind V1 系统总体架构设计》，用于确认 EnterpriseMind 自身 PostgreSQL 的逻辑表设计。

本稿只确认：

- PostgreSQL Schema 划分。
- 表职责、关键字段和表间引用。
- 唯一性、状态、删除和数据保留规则。
- 必须由数据库保证的约束，以及必须由领域服务保证的规则。
- 上传、覆盖、处理激活、回收站、Agent 确认和 Database MCP 查询的事务边界。

本文本身不嵌入：

- ER 图。
- 可执行 DDL、迁移脚本和初始化数据；这些实现产物可依据本确认稿生成。
- PostgreSQL 参数、连接池和部署资源配置。
- 企业业务数据库内部表设计。企业业务数据库只通过 Database MCP 只读接入，不属于 EnterpriseMind 数据模型。

文档状态：`Confirmed`。本表设计作为首版迁移、Repository 模型和接口实现的基线。

## 2. 总体结论

### 2.1 数据库边界

EnterpriseMind V1 使用一个自身 PostgreSQL 数据库，并启用 pgvector。逻辑上划分为 6 个 Schema：

| Schema | 职责 |
|---|---|
| `iam` | 用户、部门和本地账号 |
| `knowledge` | 知识库、目录、文档、解析结果、Chunk、Embedding、处理任务和回收站 |
| `agent` | 会话、消息、Agent Run、Tool、人工确认、引用、Memory 和生成物 |
| `integration` | Database MCP 数据源、Schema 快照、关系白名单和部门授权 |
| `infra` | MinIO 对象登记和 Transactional Outbox |
| `langgraph_checkpoint` | LangGraph PostgreSQL Checkpointer 自主管理的内部表 |

这些 Schema 只是同一模块化单体数据库内的命名空间，不表示拆分为多个数据库或微服务。

数据库版本基线确定为：

- `PostgreSQL 18.6`。
- `pgvector 0.8.6`。
- PostgreSQL 内置扩展 `pg_trgm`。

选择依据：PostgreSQL 18.6 是当前 18 大版本的稳定小版本，官方支持期至 2030-11-14；PostgreSQL 19 当前仍为 Beta，不进入生产基线。pgvector 0.8.6 是当前最新正式标签，官方同时提供 PostgreSQL 18 对应的构建标签。版本依据见 [PostgreSQL Versioning Policy](https://www.postgresql.org/support/versioning/) 和 [pgvector v0.8.6](https://github.com/pgvector/pgvector/tree/v0.8.6)。

生产部署固定完整版本和容器镜像 digest，不直接使用会漂移的 `latest`、`pg18` 等浮动标签。PostgreSQL 18 大版本内及时跟进官方安全和缺陷修复小版本；升级到 19 或更高大版本必须单独评估、备份和演练。

### 2.2 表数量

本稿设计 35 张 EnterpriseMind 管理表：

| 领域 | 数量 | 表 |
|---|---:|---|
| 身份 | 2 | `departments`、`users` |
| 知识与文档 | 14 | `knowledge_bases`、`folders`、`documents`、`document_revisions`、`document_artifacts`、`deletion_batches`、`processing_tasks`、`processing_units`、`source_units`、`content_elements`、`source_anchors`、`chunks`、`chunk_anchors`、`chunk_embeddings` |
| Agent | 10 | `conversations`、`messages`、`conversation_summaries`、`agent_runs`、`tool_calls`、`pending_actions`、`pending_action_targets`、`answer_sources`、`memory_items`、`generated_artifacts` |
| Database MCP | 7 | `database_sources`、`schema_snapshots`、`schema_relations`、`schema_columns`、`schema_constraints`、`relation_policies`、`relation_department_grants` |
| 基础设施 | 2 | `storage_objects`、`outbox_events` |

`langgraph_checkpoint` 中的内部表由锁定版本的 LangGraph PostgreSQL Checkpointer 初始化和迁移，不由 EnterpriseMind 业务迁移重复定义，也不允许领域代码直接读写。

### 2.3 不建立的表

V1 明确不建立以下关系：

- `tenants`：系统为单企业私有化部署，业务表不增加无效的 `tenant_id`。
- `roles`、`permissions`、`user_roles`：系统角色只有管理员和普通用户，使用 `users.role` 和确定性授权服务。
- `login_sessions`：需求未定义长期登录会话、设备管理或 Token 撤销功能，V1 不提前建立 PostgreSQL 会话表；认证令牌方案在 API 设计中确定。
- `knowledge_base_members`：知识库成员根据知识库类型、用户部门和状态动态计算。
- `document_permissions`、`folder_permissions`：V1 无文档级、文件夹级 ACL。
- `document_versions`：面向用户不提供版本管理；`document_revisions` 仅服务于内部处理代次和覆盖一致性。
- `model_configs`、`prompt_versions`：模型和 Prompt 继续由配置文件与 Git 管理。
- `database_query_results`、`query_executions`：Database MCP 查询结果和 SQL 执行记录不持久化；回答所需的数据来源直接保存在 `answer_sources`，大结果写入 MinIO 导出文件。
- `operation_logs`、`security_events`、`sql_audit_logs`：V1 不建设持久化操作或 SQL 审计能力；运行诊断进入脱敏的服务日志和指标。

## 3. 通用字段与约定

### 3.1 主键、时间和并发

- 业务主键统一为 `bigint GENERATED ALWAYS AS IDENTITY`，由 PostgreSQL 生成自增值；外键统一使用 `bigint`。
- 所有时间均使用 `timestamptz`，数据库和服务端以 UTC 保存，客户端按时区展示。
- 可修改的聚合根使用 `row_version bigint` 做乐观并发控制，包括用户、部门、知识库、文件夹、文档、会话、Memory 和 Database MCP 策略。
- 普通可修改表包含 `created_at`、`updated_at`；只追加的历史表仅保留 `created_at` 或明确的开始、结束时间。
- 只在权限或明确产品元数据需要时保存用户引用，例如文档上传人、会话所有者、Memory 所属用户和生成文件所有者；不增加仅用于审计“谁创建、谁修改”的字段。

### 3.2 状态字段

V1 使用 `varchar` 加数据库 `CHECK` 约束，不使用 PostgreSQL 原生 ENUM。这样可以在不停机迁移中增加状态，又能阻止非法值进入数据库。

状态变化同时受三层保护：

1. 领域服务只允许定义好的状态边。
2. 更新时携带 `row_version`，防止并发覆盖。
3. 数据库 `CHECK` 保证状态值合法；关键跨表不变量由事务和约束触发器保证。

### 3.3 名称规范化

需要唯一判断的名称同时保存：

- `name`：用户可见原值。
- `name_key`：应用进行 Unicode 规范化、首尾空白处理和大小写折叠后的比较值。

用户名使用同样方式生成 `username_key`。数据库唯一索引建立在规范化字段上，避免仅通过大小写、全半角或不可见首尾空白制造重复对象。

### 3.4 JSONB 使用边界

JSONB 只用于结构随文件格式或 Provider 变化、且不承担核心关联和权限判断的数据，例如：

- 文档元素的表格、代码和图片语义载荷。
- 来源锚点的格式专属定位信息。
- Tool 参数与摘要结果。
- 生成文件的数据来源说明。

用户、部门、知识库归属、文档代次、权限白名单、处理状态和引用关系必须使用普通列与外键，不放入 JSONB。

### 3.5 删除规则

- 知识库、文件夹和文档使用 30 天回收站，保留 `deleted_at`、`purge_after` 和 `deletion_batch_id`。
- 会话经用户确认后物理删除；Memory 由所有者直接删除，不创建二次确认。两者均不进入回收站，也不保留被删除正文副本。
- 用户和部门不做通用软删除：用户以 `disabled` 停用；部门只有在无用户和知识库关联时才允许物理删除。
- MinIO 文件删除采用“数据库先标记、Outbox 驱动、Worker 幂等清理”的最终一致方式；RAG 可见性必须在数据库事务中立即关闭，不能等待对象存储清理完成。

## 4. `iam`：身份与登录

### 4.1 `iam.departments`

部门主表。V1 仅支持平级部门，因此不设计 `parent_id`。

| 字段 | 类型 | 可空 | 说明 |
|---|---|---:|---|
| `id` | `bigint` | 否 | 主键 |
| `name` | `varchar(200)` | 否 | 展示名称 |
| `name_key` | `varchar(200)` | 否 | 规范化比较值，唯一 |
| `status` | `varchar(20)` | 否 | `active` / `disabled` |
| `row_version` | `bigint` | 否 | 乐观锁版本 |
| `created_at` / `updated_at` | `timestamptz` | 否 | 创建、更新时间 |

关键规则：

- `name_key` 全局唯一。
- 删除前必须确认不存在任何 `users.department_id` 和 `knowledge_bases.department_id` 引用。
- Database MCP 的部门关系授权是依附数据，删除部门时同步删除，不额外阻止部门删除。
- 部门停用不解除关系，但普通成员不能再通过该部门获得知识库或 Database MCP 权限。

### 4.2 `iam.users`

本地账号和系统角色主表。

| 字段 | 类型 | 可空 | 说明 |
|---|---|---:|---|
| `id` | `bigint` | 否 | 主键 |
| `username` | `varchar(100)` | 否 | 用户名原值 |
| `username_key` | `varchar(100)` | 否 | 规范化登录名，全局唯一 |
| `password_hash` | `text` | 否 | 强哈希结果，不保存明文或可逆密文 |
| `credential_version` | `bigint` | 否 | 凭据版本，初始为 1；管理员重置密码时递增，用于使旧访问令牌失效 |
| `role` | `varchar(20)` | 否 | `admin` / `user` |
| `department_id` | `bigint` | 是 | 普通用户必填，管理员可空 |
| `status` | `varchar(20)` | 否 | `active` / `disabled` |
| `row_version` | `bigint` | 否 | 乐观锁版本 |
| `created_at` / `updated_at` | `timestamptz` | 否 | 创建、更新时间 |

关键规则：

- `role = 'user'` 时 `department_id` 必须非空。
- `credential_version >= 1`；访问令牌携带签发时版本，每次请求与本行当前值比较。
- 普通用户登录和授权时要求用户、所属部门均为 `active`。
- 管理员有权管理所有知识库并查询所有全局白名单关系；管理员可不绑定部门。
- 全新系统迁移完成后，初始化步骤仅在 `users` 为空时使用部署提供的用户名和密码 Secret 创建一个 `active` 管理员；重复执行不得创建第二个账号、覆盖账号或重置密码。表非空但不存在管理员时视为异常，不自动提权任何账号。
- 管理员重置用户密码时锁定目标用户，校验 `row_version`，在同一事务更新 `password_hash`、递增 `credential_version`、`row_version` 和 `updated_at`；失败时所有字段保持原值。

## 5. `knowledge`：知识库、文档和检索

### 5.1 `knowledge.knowledge_bases`

知识库聚合根。

| 字段 | 类型 | 可空 | 说明 |
|---|---|---:|---|
| `id` | `bigint` | 否 | 主键 |
| `name` / `name_key` | `varchar(200)` | 否 | 展示名称和规范化比较值 |
| `type` | `varchar(20)` | 否 | `public` / `department` |
| `department_id` | `bigint` | 是 | 部门知识库必填，公共知识库必须为空 |
| `description` | `text` | 是 | 可参与检索的描述 |
| `row_version` | `bigint` | 否 | 迁移、重命名、删除确认使用 |
| `deleted_at` | `timestamptz` | 是 | 进入回收站时间 |
| `purge_after` | `timestamptz` | 是 | 永久清理时间 |
| `deletion_batch_id` | `bigint` | 是 | 级联删除批次 |
| `created_at` / `updated_at` | `timestamptz` | 否 | 创建、更新时间 |

关键规则：

- 类型和 `department_id` 必须满足条件约束。
- 活跃公共知识库之间 `name_key` 唯一；同一部门的活跃部门知识库之间 `name_key` 唯一。
- 迁移部门知识库只更新 `department_id` 和 `row_version`，不更新文档、Chunk 或 Embedding。
- 删除时由同一删除批次标记其当前活跃的文件夹和文档。

### 5.2 `knowledge.folders`

知识库内的多级目录。

| 字段 | 类型 | 可空 | 说明 |
|---|---|---:|---|
| `id` | `bigint` | 否 | 主键 |
| `knowledge_base_id` | `bigint` | 否 | 所属知识库，创建后不可跨知识库修改 |
| `parent_id` | `bigint` | 是 | 父目录，空表示知识库根目录 |
| `name` / `name_key` | `varchar(255)` | 否 | 名称和规范化比较值 |
| `row_version` | `bigint` | 否 | 移动、重命名、删除确认使用 |
| `deleted_at` | `timestamptz` | 是 | 进入回收站时间 |
| `purge_after` | `timestamptz` | 是 | 永久清理时间 |
| `deletion_batch_id` | `bigint` | 是 | 所属删除批次 |
| `created_at` / `updated_at` | `timestamptz` | 否 | 创建、更新时间 |

关键规则：

- 父目录必须与子目录属于同一知识库；使用复合外键保证。
- 同一知识库根目录内，以及同一父目录内，活跃文件夹的 `name_key` 唯一。
- 目录不能移动到自身或任意后代下。该规则需要服务层递归检查、行锁和数据库约束触发器共同保证。
- V1 只允许知识库内部移动，不允许借“移动目录”绕过知识库管理权限完成跨知识库迁移。

### 5.3 `knowledge.documents`

用户可见的逻辑文档。原文件和每次覆盖的物理属性位于 `document_revisions`。

| 字段 | 类型 | 可空 | 说明 |
|---|---|---:|---|
| `id` | `bigint` | 否 | 主键 |
| `knowledge_base_id` | `bigint` | 否 | 所属知识库，V1 创建后不跨库移动 |
| `folder_id` | `bigint` | 是 | 所属目录，空表示知识库根目录 |
| `name` / `name_key` | `varchar(255)` | 否 | 用户可修改的文档名及比较值 |
| `description` | `text` | 是 | 用户可修改，参与检索 |
| `created_by` | `bigint` | 否 | 首次创建者 |
| `processing_status` | `varchar(30)` | 否 | `pending` / `processing` / `success` / `partial_success` / `failed` |
| `latest_revision_no` | `integer` | 否 | 最近创建的内部代次号，从 1 递增 |
| `active_revision_id` | `bigint` | 是 | 当前唯一可参与检索的代次 |
| `row_version` | `bigint` | 否 | 覆盖、移动、重命名、删除确认使用 |
| `deleted_at` | `timestamptz` | 是 | 进入回收站时间 |
| `purge_after` | `timestamptz` | 是 | 永久清理时间 |
| `deletion_batch_id` | `bigint` | 是 | 所属删除批次 |
| `created_at` / `updated_at` | `timestamptz` | 否 | 创建、更新时间 |

关键规则：

- `folder_id` 为空时，同一知识库根目录下活跃文档的 `name_key` 唯一；不为空时，同一目录下唯一。
- `folder_id` 必须与文档属于同一知识库，使用复合外键保证。
- API 的有效状态在 `deleted_at IS NOT NULL` 时统一返回 `recycle_bin`；数据库仍保留删除前的 `processing_status`，方便恢复。
- `active_revision_id` 必须指向同一文档的代次。
- 所有 RAG 查询必须同时过滤知识库和文档未删除、Chunk 就绪、Chunk 的 `revision_id = active_revision_id`，且该活跃代次状态为 `success` 或可激活的 `partial_success`。这里不使用最新代次的聚合处理状态遮蔽旧活跃代次。

### 5.4 `knowledge.document_revisions`

文档内部处理代次。该表不向用户提供历史版本浏览或恢复能力。

| 字段 | 类型 | 可空 | 说明 |
|---|---|---:|---|
| `id` | `bigint` | 否 | 主键 |
| `document_id` | `bigint` | 否 | 所属逻辑文档 |
| `revision_no` | `integer` | 否 | 文档内单调递增代次号 |
| `trigger_type` | `varchar(30)` | 否 | `initial_upload` / `overwrite` / `generated_write` |
| `original_object_id` | `bigint` | 否 | MinIO 原文件登记 |
| `original_file_name` | `varchar(500)` | 否 | 上传时原始文件名 |
| `file_extension` | `varchar(20)` | 否 | 规范化扩展名 |
| `mime_type` | `varchar(200)` | 否 | 经服务端检测的 MIME |
| `size_bytes` | `bigint` | 否 | 文件大小 |
| `content_sha256` | `char(64)` | 否 | 内容摘要，用于完整性和幂等判断 |
| `processing_status` | `varchar(30)` | 否 | 与文档处理状态集合一致 |
| `initiated_by` | `bigint` | 否 | 上传或确认覆盖的用户 |
| `activated_at` | `timestamptz` | 是 | 成为活跃检索代次的时间 |
| `retired_at` | `timestamptz` | 是 | 退出检索的时间 |
| `failure_summary` | `jsonb` | 是 | 失败阶段和数量摘要，不代替明细 |
| `created_at` / `updated_at` | `timestamptz` | 否 | 创建、更新时间 |

关键规则：

- `(document_id, revision_no)` 唯一。
- 覆盖确认后，在一个事务中锁定文档、创建新代次、递增 `latest_revision_no`，并创建处理任务与 Outbox；如果已有 `active_revision_id`，此时保持不变，旧内容继续参与 RAG。
- 新代次达到 `success`，或达到满足激活条件的 `partial_success` 后，事务性把 `active_revision_id` 切换为新代次，并将旧代次标记为退出检索。
- 覆盖后的新代次失败时继续使用旧活跃代次，不需要执行“回退”写操作；首次上传失败时因不存在旧代次而保持无可检索内容。

### 5.5 `knowledge.document_artifacts`

登记某个文档代次产生的预览文件和派生文件。

| 字段 | 类型 | 可空 | 说明 |
|---|---|---:|---|
| `id` | `bigint` | 否 | 主键 |
| `revision_id` | `bigint` | 否 | 所属文档代次 |
| `source_unit_id` | `bigint` | 是 | 可选的页、Slide、Sheet 等来源单元 |
| `artifact_type` | `varchar(40)` | 否 | `preview_pdf`、`page_image`、`thumbnail`、`ocr_payload`、`vision_payload` 等 |
| `storage_object_id` | `bigint` | 否 | MinIO 对象登记 |
| `status` | `varchar(20)` | 否 | `pending` / `ready` / `failed` |
| `metadata` | `jsonb` | 是 | 尺寸、页码、转换器版本等补充信息 |
| `created_at` / `updated_at` | `timestamptz` | 否 | 创建、更新时间 |

同一代次、来源单元和派生物类型不得重复生成记录。

### 5.6 `knowledge.deletion_batches`

记录一次文档、目录树或知识库级联进入回收站的边界。

| 字段 | 类型 | 可空 | 说明 |
|---|---|---:|---|
| `id` | `bigint` | 否 | 主键 |
| `root_type` | `varchar(30)` | 否 | `knowledge_base` / `folder` / `document` |
| `root_id` | `bigint` | 否 | 删除时的根对象 ID，作为历史快照而非多态外键 |
| `root_name` | `varchar(255)` | 否 | 删除时名称快照 |

## 9. 关键跨表不变量

数据库迁移实现时必须把下列不变量落为外键、唯一索引、`CHECK` 或约束触发器；仅写在代码注释中不算完成。

1. 普通用户必须且只能属于一个部门；管理员可不属于部门。
2. 公共知识库不能绑定部门，部门知识库必须绑定部门。
3. 父子文件夹、文档与文件夹、文档代次与文档必须属于同一知识库或同一文档。
4. 文件夹不能形成环。
5. 同目录活跃文档和同父目录活跃文件夹名称唯一；进入回收站后不占用名称。
6. 文档只能引用自身的 `active_revision_id`；一个文档同时最多一个活跃代次。
7. Chunk 冗余的 `document_id`、`knowledge_base_id` 必须与其代次一致。
8. 回答来源必须二选一：创建时知识库来源校验 Chunk/Anchor，数据库来源校验 Database Tool Call、数据源和 Schema 快照；底层来源删除后保留定位快照字段。
9. Tool 幂等键对同一执行主体唯一。
10. Pending Action 幂等键对同一执行主体唯一；响应用户必须等于创建时绑定用户，且状态只能从 `pending` 解析一次。
11. V1 最多一条 Database MCP 数据源配置；该数据源最多一个 active Schema 快照。
12. 部门关系授权只能引用已进入全局白名单的策略；执行时仍要确认策略 enabled、部门 active、关系存在于当前快照。

以下规则需要领域服务在事务中执行，数据库约束不能独立完成全部语义：

- 最终权限判断和 LLM 参数不可信校验。
- 文件夹环检测时的并发锁定。
- 高风险操作二次确认、参数哈希、资源版本和有效期复核。
- `partial_success` 是否达到可激活标准。
- 覆盖、回收站恢复和永久清理的多表状态切换。
- SQL AST 只读检查、危险函数检查、超时和行数上限。

## 10. 关键事务设计

### 10.1 初次上传

1. 服务端以随机 Object Key 上传到 MinIO，并验证对象大小和摘要。
2. 在单个 PostgreSQL 事务中创建 `storage_objects`、`documents`、`document_revisions`、`processing_tasks`、初始 `processing_units` 和 `outbox_events`。
3. 事务提交后 Dispatcher 投递 Redis。
4. 如果数据库事务失败，对象成为未登记孤儿，由定期扫描按安全时间窗清理。

### 10.2 覆盖文档

1. 锁定文档并复核确认请求中的 `row_version`、目标 ID、名称和用户权限。
2. 创建新 Storage Object 与新 `document_revision`。
3. 同一事务中保留当前 `active_revision_id`、递增代次号、更新处理状态并创建任务与 Outbox。
4. 新代次完整成功，或达到可激活的 `partial_success` 条件后，原子切换 `active_revision_id`；旧 Chunk 此时退出检索，旧物理对象和派生数据由可靠清理事件异步删除。
5. 新代次处理失败时 `active_revision_id` 保持不变；首次上传因没有旧代次而保持无可检索内容。

### 10.3 处理完成与激活

Worker 更新处理单元后，在事务中重新确认：

- 任务针对文档最新代次。
- 文档和知识库不在回收站。
- 必需阶段已完成。
- 可检索 Chunk 的关键词索引已就绪；需要向量召回的 Chunk 有 active 模型 Embedding。

满足条件后才更新代次、文档聚合状态和 `active_revision_id`。迟到的旧 Worker 结果可以落历史状态，但不能重新激活旧代次。

### 10.4 删除、恢复与永久清理

- 删除：创建 `deletion_batch`，锁定根对象并递归标记当前活跃后代；RAG 过滤条件立即生效。
- 恢复：只恢复同一批次的对象，校验父级有效和名称未冲突；若冲突，先要求用户重命名或调整目标位置。
- 到期清理：把批次切换为 `purging`，将 Storage Object 标为 `pending_delete` 并写 Outbox；Worker 删除 MinIO 后再物理清理数据库内容。
- 清理失败：保留对象登记、批次和失败原因，可幂等重试；成功后物理删除批次，不保留清理历史。

### 10.5 高风险操作与 Tool

Agent 来源创建 `tool_calls`、`pending_actions` 和目标快照后暂停 Run；页面资源接口只创建 `origin = api` 的 Pending Action 和目标快照，不伪造会话、消息或 Run。用户确认时锁定 Pending Action，验证响应者、有效期、幂等键和 binding hash；领域操作执行前再次鉴权并核对每个目标 `row_version`。任一绑定条件变化都使原确认失效，不能静默改参数继续执行。

### 10.6 Schema 刷新和查询

- Schema 刷新始终写新快照，不原地修改 active 快照。
- 完整抓取成功后，在一个事务中切换 `database_sources.active_snapshot_id`。
- 每轮查询在当前 Tool Call 内固定 Schema 快照 ID；SQL Guard 和 MCP Server 对相同快照范围做两次对象校验。
- SQL 与结果集不持久化，也不进入 `tool_calls`、Checkpoint、服务日志或指标；最终回答只把回答时的数据源名称、数据库名称、关系、查询时间、查询条件和截断标志写入 `answer_sources`。

## 11. 索引设计原则

首版迁移应至少包含以下索引，具体名称和 SQL 在实现阶段确定：

| 场景 | 索引策略 |
|---|---|
| 用户登录 | `users(username_key)` 唯一索引 |
| 动态权限 | `users(department_id, status)`、`knowledge_bases(type, department_id, deleted_at)` |
| 目录浏览 | `folders(knowledge_base_id, parent_id, deleted_at, name_key)` |
| 文档同名判断 | 根目录和非根目录分别建立活跃记录部分唯一索引 |
| 回收站清理 | 各回收对象的 `(purge_after)` 部分索引，条件为已删除 |
| 处理调度 | `processing_tasks(status, created_at)`、`processing_units(status, lease_expires_at)` 部分索引 |
| Outbox | `outbox_events(status, next_attempt_at)` 部分索引 |
| 关键词检索 | `chunks.search_vector` GIN；文件名、描述和文件夹名称使用 `pg_trgm` GIN/GiST |
| 向量检索 | 按 active `model_key + dimensions` 建立 pgvector HNSW 表达式部分索引 |
| 会话历史 | `messages(conversation_id, sequence)` 唯一索引，使用 Keyset Pagination |
| Agent 运维 | `agent_runs(status, created_at)`、`tool_calls(agent_run_id, created_at)`、`pending_actions(actor_user_id, idempotency_key)` 唯一索引、非空 Run 的 pending 部分唯一索引 |
| Memory | `memory_items(user_id, category, updated_at)`，必要时增加用户内 fingerprint 索引 |
| Schema 权限 | `relation_policies(database_source_id, schema_name, relation_name)` 唯一索引和授权反向索引 |

V1 不预先分区。上线数据量表明 `messages` 或 `chunks` 达到维护瓶颈后，再按实际增长率制定分区迁移，避免过早增加开发和备份复杂度。

## 12. 数据保留和级联建议

| 数据 | 删除/保留策略 |
|---|---|
| 用户 | 停用优先，不级联删除其会话和文档 |
| 部门 | 只有无用户和知识库引用时物理删除 |
| 知识库/文件夹/文档 | 回收站 30 天，随后可靠永久清理 |
| 文档代次和解析数据 | 随文档永久删除；覆盖旧代次在退出检索后异步清理 |
| 会话、消息、摘要、回答来源 | 用户确认删除会话后物理级联删除 |
| Agent 中间 Checkpoint | `completed` 或 `failed` 业务终态提交后删除；`cancelled` 保留到继续执行或会话删除，最终状态保留在 `agent_runs` |
| Memory | 用户删除后物理删除正文 |
| Database MCP 查询结果 | 不持久化；用户明确请求的导出结果作为生成文件保存到 MinIO |
| 处理任务与单元 | 随文档代次清理，不额外保留尝试历史 |
| Outbox | 已发布事件在可配置保留窗口后批量删除 |

所有 `ON DELETE` 行为需要显式定义。默认使用 `RESTRICT`；只有明确的聚合内部数据才使用 `CASCADE`，业务历史引用优先 `SET NULL` 或保留目标快照。

## 13. 设计确认清单

### 13.1 已确认

1. **数据库基线（已确认）**：采用 `PostgreSQL 18.6 + pgvector 0.8.6 + pg_trgm`。生产镜像固定精确版本和 digest；在 PostgreSQL 18 大版本内跟进官方安全和缺陷修复小版本，不采用 PostgreSQL 19 Beta。

2. **主键（已确认）**：V1 使用 `bigint GENERATED ALWAYS AS IDENTITY` 自增主键，不使用 UUID；所有外键使用 `bigint`。
3. **名称唯一性（已确认）**：用户名、同范围知识库、同级文件夹和同目录文档采用 NFKC、trim、casefold 后唯一。
4. **跨知识库移动（已确认）**：V1 文件夹和文档只允许知识库内部移动，不提供跨知识库迁移。
5. **覆盖失败语义（已确认）**：覆盖处理期间继续使用旧活跃代次；新代次达到可激活成功条件后原子切换，切换后旧内容退出。新代次失败时保持旧内容。
6. **部分成功激活线（已确认）**：至少存在一个完整通过 Chunk、关键词索引和 Embedding，且具备同代次有效来源锚点的可检索单元，才允许 `partial_success` 激活；否则为 `failed`。
7. **Embedding 维度（已确认）**：表设计不写死维度；选定首个 Embedding Provider 后，为 active 模型建立固定维度 HNSW 表达式部分索引。
8. **Checkpoint 所有权（已确认）**：由锁定版本的 LangGraph PostgreSQL Checkpointer 管理独立 Schema，业务层只维护 `agent_runs`，不复制框架内部协议。
9. **日志审计（已确认）**：V1 不建立 `operation_logs`、`security_events`、`query_executions` 或 SQL 审计记录。Database MCP 的 SQL 和结果集不持久化；回答所需来源直接保存在 `answer_sources`。
10. **管理员 Database MCP 查询范围（已确认）**：管理员可查询当前快照内全部全局白名单关系，普通用户还必须满足部门授权。
11. **项目名称（已确认）**：产品、代码和文档统一使用 `EnterpriseMind`，不再使用旧项目名。
12. **账号初始化与密码重置（已确认）**：空系统初始化时从部署 Secret 幂等创建首个管理员；V1 只允许管理员重置用户密码，并通过 `credential_version` 使旧令牌失效。

以上设计项均已确认。本表设计可作为首版迁移、Repository 模型和 API 详细设计的输入；后续字段调整应通过迁移完成，不直接修改生产表结构。
