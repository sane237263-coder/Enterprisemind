# EnterpriseMind V1 内容分块、来源锚点与索引结构设计（确认稿）

## 1. 文档目的

本文档细化 EnterpriseMind V1 文档解析结果如何形成可检索 Chunk、如何保存可定位来源锚点，以及关键词和向量索引如何组织。

本设计直接复用已经确定的：

- `knowledge.source_units`
- `knowledge.content_elements`
- `knowledge.source_anchors`
- `knowledge.chunks`
- `knowledge.chunk_anchors`
- `knowledge.chunk_embeddings`
- `agent.answer_sources`

本文不新增业务表、文档字段、用户页面或独立搜索接口，也不改变已确认的权限、覆盖、回收站和文档级处理状态语义。Chunk 长度、overlap、候选数、RRF 常量、Rerank 阈值和 HNSW 参数以《检索增强生成参数与离线评测方案》（确认稿）为准。

可执行迁移和代码可以在本设计确认后实施，不再作为项目级限制。

## 2. 核心不变量

1. `source_unit → content_element → source_anchor` 表示原文件结构和定位，`chunk → chunk_anchor` 表示检索内容到原文的映射，两者不能合并成一张无结构文本表。
2. 每个 `ready` Chunk 必须至少关联一个属于同一 `revision_id` 的来源锚点。
3. Chunk 的合成标题、格式标签等辅助文本不能冒充原文；只有锚点覆盖的文本才能作为原文引用。
4. 知识库事实写入 `answer_sources` 时，创建时必须同时选择实际使用的 Chunk 和来源锚点。
5. 关键词和向量召回必须应用完全相同的权限、回收站、活跃代次和 Chunk 状态过滤。
6. 文档覆盖、重命名或移动不能通过复制旧权限或路径到 Chunk 中形成过期授权结果。
7. `partial_success` 只允许完整通过 Chunk、关键词索引、当前模型 Embedding 和锚点校验的单元参与 RAG。
8. 失败部分重试不能修改、重排或重复生成已经成功且可能被引用的 Chunk。
9. Redis 消息、应用日志和指标不携带 Chunk 正文、原文片段、Embedding 或 MinIO Object Key。

## 3. 数据层级与职责

| 层级 | 数据 | 职责 | 不承担的职责 |
|---|---|---|---|
| 来源单元 | `source_units` | 表示文档、页、Slide、Sheet 或独立图片 | 不直接作为检索结果 |
| 内容元素 | `content_elements` | 保存标题、段落、列表、表格、代码、图片说明等结构 | 不表达最终上下文长度 |
| 来源锚点 | `source_anchors` | 保存原文件中的可定位范围和对应文本 | 不保存回答排序 |
| Chunk | `chunks` | 保存供关键词召回、Rerank 和 LLM 使用的内容 | 不保存用户权限副本 |
| Chunk—锚点 | `chunk_anchors` | 把 Chunk 内容范围映射回一个或多个原文位置 | 不代替来源元素结构 |
| Embedding | `chunk_embeddings` | 保存指定模型对 Chunk 的向量表示 | 不决定 Chunk 是否有权访问 |
| 回答来源 | `answer_sources` | 固化本次回答实际采用的短引用和定位快照 | 不作为长期文档副本或审计日志 |

## 4. 来源单元设计

### 4.1 各格式的来源单元

`source_units.ordinal` 从 0 开始，只要求在同一代次、同一 `unit_type` 内稳定。面向用户的页码、Slide 编号等仍从 1 开始，保存在锚点定位结构中。

| 文件格式 | `unit_type` | 划分规则 | `label` |
|---|---|---|---|
| PDF | `page` | 每页一个来源单元 | 可空 |
| DOC/DOCX | `document` | 整个文档一个来源单元，段落结构由元素和锚点表达 | 文档标题，可空 |
| PPT/PPTX | `slide` | 每个 Slide 一个来源单元 | Slide 标题，可空 |
| XLS/XLSX | `sheet` | 每个 Sheet 一个来源单元 | Sheet 名 |
| CSV | `sheet` | 整个文件作为一个虚拟 Sheet | 文件名或 `CSV` |
| Markdown/TXT | `document` | 整个文件一个来源单元 | 可空 |
| PNG/JPG/JPEG/WEBP | `image` | 整张图片一个来源单元 | 文件名，可空 |

PDF 页、PPT Slide 中的内嵌图片不额外创建无父级关系的 `image` 来源单元，而是在所属 `page` 或 `slide` 中创建 `image` 内容元素。这样图片锚点天然保留页或 Slide 范围。`image` 来源单元只用于独立图片文件。

### 4.2 来源单元文本

- `extracted_text` 保存该单元可读文本的顺序拼接结果，用于预览校验和文本偏移定位。
- 原始结构仍以 `content_elements` 为准，不能只根据 `extracted_text` 重建表格、代码或图片关系。
- `width` 和 `height` 只用于存在二维坐标的页、Slide 或图片，并与预览服务使用同一坐标系。
- `metadata` 只保存格式专属且非权限信息，例如页面旋转归一化结果；不能保存用户、部门或知识库授权副本。

## 5. 内容元素设计

### 5.1 元素顺序与父子关系

- `ordinal` 表示来源单元内的解析顺序，从 0 开始。
- `parent_element_id` 只表达同一来源单元内的结构父级，例如标题下的段落、列表项、表格标题或图片说明。
- 标题层级通过父子关系和 `structured_payload.level` 表达，不把完整标题路径重复写入每个元素。
- `status = failed` 的元素不能进入 Chunk；其失败位置由处理单元和代次失败摘要表达。

### 5.2 结构载荷最小约定

`structured_payload` 按 `element_type` 使用以下最小结构。未列出的解析器私有字段不得直接传给前端或 LLM。

| `element_type` | 必需或允许的核心内容 |
|---|---|
| `heading` | `level`；标题正文写入 `content_text` |
| `paragraph` | 正文写入 `content_text`，可记录 `text_origin` |
| `list` | `list_level`、`ordered`；列表正文写入 `content_text` |
| `table` | `table_name`、`headers`、`rows`、`merged_ranges`、`source_range` |
| `code` | `language`；原代码写入 `content_text` |
| `image` | `ocr_text`、`vision_description`、`text_origin`，按实际处理结果填写 |
| `caption` | 说明正文写入 `content_text`，通过父级关联表格或图片 |

约束：

- `text_origin` 只允许 `native`、`ocr` 或 `vision`，用于区分原生文本、OCR 文本和模型生成的图片语义说明。
- 表格必须保留表头、行列、单元格值、合并区域和原始范围，不能只保存扁平化自然语言。
- 代码语言未知时使用 `plain_text`，不能由模型猜测一个确定语言。
- Vision 描述属于派生语义，不得在界面上标成逐字原文。

## 6. 来源锚点定位结构

### 6.1 通用坐标与偏移约定

- 页码、Slide 编号、Sheet 序号和行号使用从 1 开始的用户编号。
- `char_start` 包含起始位置，`char_end` 不包含结束位置，均使用从 0 开始的 Unicode 字符位置。
- 二维坐标原点统一位于预览左上角，`x` 向右、`y` 向下。
- Bounding Box 使用 `{x, y, width, height}`，单位与 `source_units.width/height` 一致，不使用解析器原始坐标系。
- 页面旋转必须在写入锚点前归一化；前端不再次推断旋转方向。
- `locator` 不保存 MinIO Object Key、签名 URL、服务器路径或权限信息。

### 6.2 `pdf`

```json
{
  "page": 3,
  "boxes": [
    {"x": 72.0, "y": 96.0, "width": 420.0, "height": 18.0}
  ]
}
```

- `page` 必填。
- `boxes` 至少一个；跨行文本可以包含多个框。
- 框必须位于对应 `page` 来源单元的宽高范围内。

### 6.3 `image`

```json
{
  "boxes": [
    {"x": 120.0, "y": 80.0, "width": 640.0, "height": 260.0}
  ]
}
```

- 用于独立图片文件。
- OCR 文本锚点应覆盖对应文字区域；Vision 对整图的说明可以覆盖整图范围。

### 6.4 `docx`

```json
{
  "heading_path": ["第二章", "部署要求"],
  "paragraph_ordinal": 18,
  "paragraph_id": "可选的文档内标识",
  "char_start": 0,
  "char_end": 42
}
```

- `paragraph_ordinal` 必填，按解析后的正文段落从 1 开始。
- `heading_path` 必填，可为空数组。
- `paragraph_id` 仅在源文件存在稳定标识时填写。
- 文本锚点的字符范围相对于该段落正文；内嵌图片等非文本对象不填写字符范围，并在解析器可提供稳定标识时填写 `object_id`。
- DOC 文件转换后也使用 `docx` 定位结构，定位目标是受控预览，不宣称可以编辑原 DOC 二进制内容。

### 6.5 `pptx`

```json
{
  "slide": 5,
  "shape_id": "27",
  "boxes": [
    {"x": 80.0, "y": 120.0, "width": 520.0, "height": 90.0}
  ],
  "char_start": 0,
  "char_end": 36
}
```

- `slide` 和 `shape_id` 必填。
- `boxes` 至少一个。
- 文本 Shape 使用相对于 Shape 文本的字符范围；非文本图片或图表不填写字符范围。
- PPT 文件转换后也使用 `pptx` 定位结构。

### 6.6 `xlsx`

```json
{
  "sheet": "销售明细",
  "sheet_ordinal": 2,
  "cell_range": "B3:F18",
  "table_name": "可选的表名"
}
```

- `sheet`、`sheet_ordinal` 和 `cell_range` 必填。
- 单元格范围使用 A1 表示法，必须属于对应 Sheet。
- XLS 文件转换后使用 `xlsx` 定位结构。
- CSV 使用单个虚拟 Sheet 和 `xlsx` 定位结构，以保留行列和单元格范围。

### 6.7 `text`

```json
{
  "start_line": 12,
  "end_line": 16,
  "char_start": 245,
  "char_end": 388
}
```

- Markdown 和 TXT 使用该结构。
- 行号范围两端都包含，字符范围仍为左闭右开。
- 字符偏移相对于对应来源单元的 `extracted_text`。

### 6.8 原文文本与摘要

- `source_anchors.source_text` 保存定位范围对应的原文、OCR 文本，或明确标识来源的 Vision 语义说明。
- Vision 语义说明写入锚点文本时必须使用 `图片语义说明：` 前缀，并由对应内容元素的 `text_origin = vision` 共同标识。
- `source_text_sha256` 对数据库中实际保存的 `source_text` UTF-8 字节计算，不先做 NFKC、trim 或大小写转换。
- `source_text` 为空时 `source_text_sha256` 也为空。
- 锚点文本与定位不一致时，该锚点不能关联到 `ready` Chunk。

## 7. Chunk 构建规则

### 7.1 输入范围

Chunk 只读取同一代次中 `status = success` 的内容元素。结构切分顺序为：

```text
来源单元顺序
→ 标题和父子结构
→ 段落、列表、表格、代码、图片等语义边界
→ 对超长结构块进行二次切分
→ 建立 Chunk 与锚点范围
```

不得先把整个文件展平成纯文本后按固定字符数切分。

### 7.2 各类型 Chunk

| `chunk_type` | 构建规则 | 必须保留的上下文 |
|---|---|---|
| `text` | 按标题下的连续段落和列表组合 | 标题路径、列表层级 |
| `table` | 按完整表格或连续行组构建，超长时按行组切分 | 表名、Sheet、表头、单元格范围；每组重复表头 |
| `code` | 优先按完整函数、类或连续代码块构建 | 语言、父标题、紧邻解释关系 |
| `image` | 组合 OCR 文本、Caption 和 Vision 语义说明 | 页或 Slide、图片区域、文本来源类型 |
| `mixed` | 只用于拆开会破坏含义的短文本与其表格、代码或图片 | 各组成元素类型和全部锚点 |

`mixed` 不能作为默认类型，也不能用来把整页、整个 Slide 或整个文档无差别合并成一个 Chunk。

### 7.3 超长切分与 overlap

- 最大长度和 overlap 都来自配置文件，本设计不写死数值。
- overlap 必须满足 `0 <= overlap < max_chunk_length`。
- overlap 只用于同一个超长结构块的相邻子块，不跨标题章节、Sheet、Slide、表格、代码块或图片边界复制内容。
- 表格不在单元格中间切分；每个子块重复必要表头，但重复表头仍映射到原表头锚点。
- 代码优先在函数、类、空行或语法块边界切分，不能从字符串或注释中间机械截断。
- 每个子块必须独立满足锚点完整性；只有辅助标题前缀可以没有对应字符范围。

### 7.4 Chunk 状态

| 状态 | 含义 | 可参与召回 |
|---|---|---:|
| `pending` | 内容和锚点已登记，但关键词或当前模型 Embedding 尚未全部通过 | 否 |
| `ready` | 关键词、当前模型 Embedding 和同代次锚点全部通过 | 是 |
| `failed` | 任一必需依赖最终失败 | 否 |
| `retired` | 进入物理清理流程的旧记录 | 否 |

正常构建只允许 `pending → ready` 或 `pending → failed`；失败部分重试允许 `failed → pending`。`ready` Chunk 在活跃代次内保持不可变，旧代次退出检索依赖 `active_revision_id`，不依赖批量改成 `retired`。

### 7.5 `content`、`metadata` 与 `context_group`

- `content` 是供 Rerank 和 LLM 使用的确定性文本表达，包含必要的标题路径或结构标签。
- 辅助结构前缀与原文正文必须可区分；`chunk_anchors.content_start/content_end` 只覆盖能映射到来源锚点的部分。
- `metadata` 只允许保存标题路径、元素类型、代码语言、表名、Sheet 名和文本来源类型等非权限检索提示。
- 文档名、描述和文件夹路径不复制到 `metadata`，避免重命名或移动后产生陈旧路径。
- `context_group` 只用于同一文档代次内的相邻合并，可表达超长元素子块、代码与解释、图片与 Caption、表格行组等关系。
- `context_group` 不能跨文档、跨代次，也不能作为权限或可见性判断依据。

### 7.6 Chunk 顺序和不可变性

- `ordinal` 表示代次内 Chunk 的稳定创建顺序，从 0 开始。
- 首次构建时按来源单元、内容元素和切分子块的确定性顺序分配。
- Chunk 与锚点首次登记时状态为 `pending`，不能参与任何召回。
- 已经 `ready` 的 Chunk 不因失败部分重试而修改内容、重新编号或复用 ID 表达另一段内容。
- 活跃 `partial_success` 代次重试成功后产生的新 Chunk，在锁定代次后从当前最大 `ordinal + 1` 继续分配；引用和相邻关系以锚点及 `context_group` 为准，不假设补建 Chunk 的 ordinal 等于原文顺序。
- 同一失败处理单元重投时，必须复用已经登记的失败 Chunk 或确认不存在结果后再创建，依赖唯一约束和租约校验避免重复。

## 8. Chunk 与锚点映射

### 8.1 字符范围

- `chunk_anchors.content_start/content_end` 使用相对于 `chunks.content` 的 0-based 左闭右开 Unicode 字符范围。
- 每个范围必须非空且不超出 Chunk 内容长度。
- 同一段 Chunk 内容可映射多个锚点；映射范围允许因 overlap 而出现在多个 Chunk 中。
- 辅助标题、类型标签等合成文本可以不被范围覆盖，但不能被保存为 `quote_text`。

### 8.2 锚点顺序

- `chunk_anchors.ordinal` 从 0 开始，按引用片段在 Chunk 内容中的首次出现位置排列。
- 同一 Chunk 和同一锚点只允许一条映射；一个锚点覆盖 Chunk 中多个连续片段时，应扩大为一个能准确表示的范围，不能准确合并时拆成更细的来源锚点。
- `quote_text` 是构建时从对应 Chunk 字符范围取得的短快照，必须能由锚点的 `source_text` 或明确标识的派生语义说明验证。

### 8.3 同代次约束

现有外键可以保证 Chunk 和锚点各自存在，但不能单独保证二者属于同一代次。迁移实现时必须增加延迟约束触发器或等价的数据库约束，保证：

```text
chunk_anchors.chunk_id → chunks.revision_id
    =
chunk_anchors.anchor_id → source_anchors.revision_id
```

领域服务在写入前也必须校验，但不能只依赖应用层约定。

## 9. 关键词索引文本

### 9.1 `search_tokens`

`search_tokens` 是从 Chunk 内容生成的检索文本，不是展示正文。生成规则：

1. 对文本做 Unicode NFKC、空白规范化和大小写折叠。
2. 中文执行与查询侧一致的预分词。
3. 英文和数字保留词项边界。
4. 代码保留完整标识符，同时补充分解后的 `camelCase`、`PascalCase`、`snake_case` 和带数字型号词项。
5. 接口名、项目代号、版本号、文件扩展名和编号不能被停用词处理删除。
6. 表格加入表名、Sheet、表头和可检索单元格值，但不把坐标 JSON 当成词项。
7. 图片加入 OCR 文本、Caption 和 Vision 描述，并保留其来源类型。

查询文本必须经过相同规范化和分词流程。不得把 `search_tokens` 作为引用原文返回给用户。

### 9.2 `search_vector`

- 使用 `to_tsvector('simple', search_tokens)` 构建，避免依赖 PostgreSQL 不具备的内置中文分词能力。
- `search_vector` 与 `search_tokens` 在同一事务中写入；任一失败时对应关键词索引单元不能成功。
- 关键词查询使用同样处理后的 `tsquery`，具体查询模式、权重和候选数量按《检索增强生成参数与离线评测方案》的确认值执行。

### 9.3 关键词召回的可变文档元数据分支

文档名称、描述和当前文件夹路径作为关键词召回内部的元数据分支参与召回：

- 文档名称使用当前 `documents.name_key`。
- 描述使用当前 `documents.description`。
- 路径通过当前文档、文件夹和祖先文件夹实时计算。
- 文件夹路径片段按当前 `folders.name_key` 匹配。

这些值不复制到 Chunk，因此同知识库内移动、重命名或修改描述后立即按新值生效，不需要重建 Chunk 或 Embedding。元数据命中文档后，只能在该文档当前活跃代次的 `ready` Chunk 中按确认配置数量映射候选，不能把整篇文档全部送入上下文；映射和关键词分支合并规则按《检索增强生成参数与离线评测方案》执行。

## 10. Embedding 输入与向量记录

### 10.1 Embedding 输入

Embedding 输入由下列稳定内容确定性组合：

- Chunk 类型。
- 标题路径或必要结构标签。
- 表名、Sheet、表头或代码语言等语义上下文。
- `chunks.content` 中的正文。

不包含：

- 用户、部门、权限范围。
- `revision_id`、`document_id` 等数据库标识。
- Locator JSON、坐标、MinIO 地址。
- 可变的文档名称、描述和文件夹路径。
- Prompt、Secret 或 Provider 凭据。

这样文档在同一知识库内移动、重命名或修改描述时不需要重新生成向量，元数据仍通过关键词通道内的独立分支参与召回。

### 10.2 模型与维度

- `model_key` 使用配置文件中的稳定逻辑标识，不保存密钥或完整请求。
- `dimensions` 必须等于向量实际维度。
- V1 同一时刻只使用一个 active Embedding 模型参与向量召回。
- 模型与维度尚未确定时不创建假定维度的 HNSW 索引。
- 新模型的建立、验证和切换继续遵守旧模型可用到新模型准备完成的语义，不在本阶段增加模型管理页面或数据库配置表。

## 11. PostgreSQL 索引结构

### 11.1 必需索引

| 用途 | 索引结构 | 说明 |
|---|---|---|
| Chunk 关键词召回 | `chunks.search_vector` 的 GIN 部分索引 | 只包含 `status = 'ready'` |
| 文档名称模糊匹配 | `documents.name_key` 的 `pg_trgm` GIN | 只包含未进回收站文档 |
| 文档描述模糊匹配 | `documents.description` 的 `pg_trgm` GIN | 只包含未删除且描述非空文档 |
| 路径片段匹配 | `folders.name_key` 的 `pg_trgm` GIN | 只包含未进回收站文件夹 |
| 活跃代次 Chunk 读取 | 现有 `chunks(revision_id, ordinal)` 唯一索引 | 从 `active_revision_id` 定位 Chunk |
| Chunk 锚点顺序 | 现有 `chunk_anchors(chunk_id, ordinal)` 唯一索引 | 返回引用顺序 |
| 锚点反向引用 | `chunk_anchors(anchor_id)` B-tree | 支持来源清理和一致性校验 |
| 来源锚点读取 | `source_anchors(source_unit_id, id)` B-tree | 支持预览和级联校验 |
| Chunk 向量召回 | active `model_key + dimensions` 的 HNSW 表达式部分索引 | 只包含 `status = 'ready'` |

不为每个历史模型永久保留 HNSW 索引，也不在 V1 预先对 Chunk 表分区。

### 11.2 HNSW 表达式索引形态

向量列不写死维度时，索引按实际模型维度使用如下结构形态：

```sql
USING hnsw ((embedding::vector(N)) vector_cosine_ops)
WHERE model_key = '<active_model_key>'
  AND dimensions = N
  AND status = 'ready'
```

其中 `N` 和模型标识必须来自已验证配置，不能直接使用用户输入。`m`、`ef_construction` 和查询期 `ef_search` 不在本阶段确定。

### 11.3 查询可见性骨架

关键词和向量查询都必须把以下条件放入数据库查询，并在授权过滤后应用候选 `LIMIT`：

```text
用户当前可访问 knowledge_base
AND knowledge_bases.deleted_at IS NULL
AND documents.deleted_at IS NULL
AND documents.active_revision_id = chunks.revision_id
AND active document_revision.processing_status IN ('success', 'partial_success')
AND chunks.status = 'ready'
```

向量查询还必须满足当前 active `model_key`、维度和 `chunk_embeddings.status = 'ready'`。不能先在全库取固定 Top-K，再在应用代码中删除无权限结果。

### 11.4 向量过滤与近似召回

pgvector 官方说明 HNSW 等近似索引会在索引扫描后应用过滤条件；当授权范围只占全库一部分时，固定扫描量可能返回不足。pgvector 0.8.0 起提供迭代索引扫描，因此 V1 采用两条确定性路径：

1. 授权且活跃的 Chunk 集合较小时，先由关系条件取得合法 `chunk_id`，通过现有 `(chunk_id, model_key)` 索引读取向量并执行精确距离排序。
2. 合法集合较大时，在同一条带权限和活跃状态条件的查询中使用 HNSW，并在事务内启用 `hnsw.iterative_scan = strict_order`，持续扫描到取得足够授权候选或达到安全扫描上限。

两条路径都只能返回已经通过 SQL 权限条件的记录。实现验收必须用 `EXPLAIN` 确认授权条件和 `LIMIT` 的执行位置；若查询计划不能让迭代扫描补足过滤后的候选，则回退精确路径。精确/近似路径切换阈值、扫描上限和召回率目标按《检索增强生成参数与离线评测方案》执行；V1 不为部门或知识库预先分区。

参考：[pgvector 官方 Filtering 与 Iterative Index Scans 说明](https://github.com/pgvector/pgvector#filtering)。

## 12. 检索候选输出边界

本文只定义关键词和向量召回提供给融合与 Rerank 的内存候选，不新增持久化表：

| 字段 | 说明 |
|---|---|
| `chunk_id` | 候选 Chunk |
| `channel` | `keyword` / `vector` |
| `match_source` | 关键词通道内区分 `chunk_content` / `document_metadata`；向量通道为 `chunk_embedding` |
| `channel_score` | 当前召回通道原始分值 |
| `channel_rank` | 当前通道内名次 |
| `content` / `token_count` | 后续 Rerank 与上下文预算使用 |
| `context_group` | 相邻合并提示 |
| `anchors` | 按 `chunk_anchors.ordinal` 返回的授权内锚点 |

RRF 公式、通道候选数、Rerank 输入数量、阈值、去重规则、相邻合并预算和最多 10 个上下文的具体执行规则以《检索增强生成参数与离线评测方案》（确认稿）为准。

## 13. 回答引用协议

### 13.1 引用选择

- LLM 得到的上下文必须携带服务端生成的候选引用标识，不能让模型自行构造文档 ID、页码或锚点。
- 知识库事实被回答采用时，Citation Service 必须从该 Chunk 已关联的锚点中选择实际支撑片段。
- 一个结论跨多个锚点时创建多个 `answer_sources`，每条记录对应一个主要锚点并按回答出现顺序排序。
- 仅有 Chunk 而没有有效锚点的内容不得作为知识库事实进入最终上下文。

### 13.2 三层文本快照

| 层级 | 字段 | 含义 |
|---|---|---|
| 原文定位 | `source_anchors.source_text` | 定位范围的原文、OCR 文本或明确标识的 Vision 说明 |
| Chunk 映射 | `chunk_anchors.quote_text` | 构建 Chunk 时可由该锚点验证的片段 |
| 回答引用 | `answer_sources.quote_text` | 本次回答实际采用的最短充分片段 |

回答引用不能默认复制整个 Chunk。`answer_sources.locator_snapshot` 保存回答时所需的最小定位结构；底层文档永久删除后保留标题和定位快照，但预览接口返回 `SOURCE_UNAVAILABLE`，不利用快照泄露已经删除的全文。

### 13.3 预览定位

- PDF/图片：打开对应页或图片并按 Box 高亮。
- DOC/DOCX：打开转换后的预览，定位标题路径和段落，字符高亮尽力完成。
- PPT/PPTX：打开 Slide，定位 Shape 和区域。
- XLS/XLSX/CSV：打开 Sheet，选中单元格范围。
- Markdown/TXT：定位行号和字符范围。

所有预览请求重新执行当前用户权限和回收站校验，不能因拥有历史 `answer_source_id` 绕过访问控制。

## 14. 部分成功与失败重试

- `ready` Chunk 只有在关键词索引和当前模型 Embedding 均成功、且至少一个同代次锚点有效时，才构成完整可检索单元。
- 解析成功但 Embedding 失败的 Chunk 不能仅凭关键词结果提前参与 RAG，因为既定 `partial_success` 激活线要求两类索引都完整。
- 活跃 `partial_success` 代次重试期间，既有完整 Chunk 保持可见。
- Chunk、锚点、`search_tokens` 和 `search_vector` 在一个数据库事务中登记，Chunk 初始为 `pending`，对应 `keyword_index` 单元在该事务成功后完成。Embedding Provider 在事务外调用并独立提交结果。
- 最后一个依赖完成时必须锁定 Chunk，重新校验关键词处理单元、当前模型 `ready` Embedding 和同代次锚点，再把 `pending` 原子改为 `ready`。
- 任一必需依赖最终失败时，仍为 `pending` 的 Chunk 转为 `failed`；不能以空关键词或缺失向量把它提前设为 `ready`。
- 重试仍失败时不撤销既有成功 Chunk，也不把活跃代次改成 `failed`。
- 旧代次退出检索由 `active_revision_id` 原子切换完成，不批量依赖 `chunks.status = retired` 实现可见性切换。

## 15. 明确不增加的设计

本设计不增加：

- 独立全文搜索页面或面向用户的任意搜索 API。
- 文档标签、文档级 ACL、跨知识库 Chunk 或跨文档 Chunk。
- Chunk 人工编辑、手动置顶、人工相关性权重或在线标注后台。
- Embedding 管理页面、数据库化模型配置或多模型同时查询。
- 单独的索引任务历史、检索历史、引用审计或 SQL 审计。
- 固定 Chunk 长度、固定 overlap、固定候选数或固定向量维度。
- 为方便检索而复制用户、部门或权限快照到 Chunk。

## 16. 必须通过的设计测试

| 场景 | 验收结果 |
|---|---|
| PDF 文本跨两行 | 一个锚点可包含多个 Box，预览高亮位置正确 |
| 扫描 PDF OCR | OCR 文本带页码和 Box，文本来源标记为 `ocr` |
| PPT 图片理解 | Vision 描述关联 Slide、Shape 和区域，不标成逐字原文 |
| XLSX 大表切分 | 按连续行组切分，每组保留表头和准确单元格范围 |
| CSV 定位 | 使用虚拟 Sheet 和 A1 单元格范围定位 |
| 代码命中 | 返回完整代码边界，并通过 `context_group` 补充相邻解释 |
| 超长段落 overlap | overlap 不跨章节，两个 Chunk 都能独立定位原文 |
| 文档重命名或移动 | 元数据检索立即使用新名称和路径，不重建 Chunk/Embedding |
| 覆盖处理中 | 两条召回通道仍只读取旧 `active_revision_id` |
| `partial_success` | 只有同时具备 Chunk、关键词、Embedding 和锚点的单元可检索 |
| 活跃部分成功代次补建 Chunk | 新 Chunk 在全部依赖完成前保持 `pending`，不能被关键词通道提前召回 |
| 失败部分重试 | 已成功 Chunk 的 ID、内容和 ordinal 不变化；新 Chunk 追加 |
| 锚点跨代次误连 | 数据库约束拒绝写入 |
| 无权限内容高分 | 在候选截断前被权限条件排除，不影响授权结果排序 |
| 授权范围较小的向量查询 | 使用合法 Chunk 集合精确排序，不因全库 HNSW 后过滤而少返回 |
| 授权范围较大的向量查询 | HNSW 迭代扫描只返回授权内容，召回率达到后续评测目标 |
| 回答引用 | 每个知识库事实来源创建时都有 Chunk 和锚点 |
| 来源永久删除 | 预览返回 `SOURCE_UNAVAILABLE`，不返回已删除全文 |

## 17. 后续设计输入

本设计已与《检索增强生成参数与离线评测方案》（确认稿）对齐，并共同确定：
