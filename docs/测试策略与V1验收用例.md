## 1. 文档目的

本文把 EnterpriseMind V1 已确认需求和详细设计转换为可执行、可复现、可留证的测试与验收规则，作为实现阶段的测试拆分、版本准入和最终验收依据。

本文不新增业务功能、页面、接口、数据表、日志审计、权限层级或部署服务。各专项设计已经定义的协议测试继续有效；本文只统一测试层级、数据、覆盖关系、发布门槛和证据要求。

## 2. 测试边界

### 2.1 本阶段覆盖

- 本地用户登录、首个管理员初始化、管理员用户/密码重置与平级部门管理。
- 公共知识库和部门知识库、文件夹、文档、同知识库内部移动与回收站。
- 上传、覆盖、解析、Office 转换、OCR/Vision、Chunk、Embedding、索引和失败部分重试。
- 混合检索、RRF、Rerank、拒答、引用创建和来源定位。
- Agent 会话、LangGraph 编排、Tool、确认、消歧、停止、恢复和 Checkpoint 清理。
- 单一企业 PostgreSQL 的 Database MCP、Schema 快照、关系授权、SQL Guard、只读执行、分页和导出。
- 用户 Memory、内容生成、生成物下载及确认后写入知识库。
- HTTP、SSE、WebSocket、Docker Compose、网络、Secret、备份恢复和容器安全。

### 2.2 明确不覆盖为产品能力

以下内容属于 V1 排除项，测试只能确认其“不存在或不可用”，不能为其设计正向功能用例：

- SaaS、多租户、第二业务数据库。
- LDAP、AD、SSO、MFA、验证码和复杂账号安全策略。
- 个人、文档、文件夹、行级或列级 ACL，以及跨部门分享。
- 审核流程、文档版本浏览、标签、评论批注和在线 Office 正文编辑。
- 独立搜索、首页仪表盘、通知中心、操作审计日志和安全事件中心。
- 模型配置后台、Prompt 在线管理、历史、回滚、A/B Test 和模型微调。
- 企业数据库写操作和复杂 BI 图表。

## 3. 验收证据等级

每项结论必须标明实际达到的证据等级，低等级证据不能替代高等级验收：

| 等级 | 证据类型 | 可证明内容 | 不能替代 |
|---|---|---|---|
| `E0` | 文档、Schema、迁移和静态检查 | 设计、声明和静态结构一致 | 运行行为 |
| `E1` | 单元测试 | 纯规则、边界和局部错误处理正确 | 真实组件集成 |
| `E2` | 集成测试 | PostgreSQL、Redis、MinIO、MCP 或 Provider 适配层交互正确 | 完整 Compose 与浏览器行为 |
| `E3` | Compose 运行验收 | 发布制品、网络、健康检查、API 和后台任务在目标拓扑运行 | 用户界面可用性 |
| `E4` | 真实浏览器验收 | 经 `reverse-proxy` 访问的页面、SSE、WebSocket、下载和引用交互正确 | 备份恢复与故障演练 |
| `E5` | 安全、并发、恢复和基准演练 | 故障、攻击、竞争和恢复边界满足要求 | 未实际执行的生产承诺 |

规则如下：

1. “代码存在”“测试通过”“镜像健康”和“接口返回 200”都不能单独记为浏览器验收通过。
2. 浏览器验收必须访问 Compose 对外入口，并保留实际交互、网络请求和页面结果证据。
3. 未执行、执行失败和环境阻塞分别记为 `未执行`、`不通过`、`阻塞`；不得写成“通过”。
4. Mock Provider 的确定性测试与真实 Provider 的连通性测试分开记录。
5. 文档中的计划命令、示例数据和预期结果不是已执行证据。

## 4. 测试类型与实现基线

### 4.1 自动化分层

| 层级 | 主要对象 | 首版实现方式 |
|---|---|---|
| 静态检查 | Python、TypeScript、配置、迁移、镜像清单 | 格式、Lint、类型、依赖锁、Compose 配置和迁移静态校验 |
| 后端单元 | 权限、名称、状态机、RRF、SQL Guard、风险解析 | `pytest` 体系下的纯函数和服务测试 |
| 前端单元 | 表单、状态展示、确认组件、引用定位参数 | React 组件与状态测试 |
| 数据库集成 | 约束、事务、锁、Outbox、Checkpoint、检索 SQL | 真实 PostgreSQL 18.6 与 pgvector 0.8.6 |
| 服务集成 | API、Redis、MinIO、MCP、Provider 适配 | 真实依赖或协议级受控替身 |
| 浏览器端到端 | 登录、上传、Agent、确认、引用、管理页面 | Playwright 驱动经反向代理交付的真实页面 |
| 部署验收 | Compose、健康检查、网络、Secret、卷和恢复 | 目标 Linux 或等价预发布主机上的发布制品 |

测试依赖必须写入项目依赖文件并锁定，不在测试脚本中临时下载。自动化测试不得要求访问生产数据或真实生产账号。

### 4.2 测试目录职责

实现阶段按职责组织，不要求把测试代码与业务代码混放：

```text
backend/tests/unit/           后端纯规则与服务单元测试
backend/tests/integration/    数据库、对象存储、队列和 MCP 集成测试
frontend/src/**/*.test.*      前端组件与状态测试
frontend/e2e/                 真实浏览器端到端测试
tests/contracts/              HTTP、SSE、WebSocket、Tool 和错误码契约
tests/security/               越权、SQL、防注入、上传和泄漏测试
tests/recovery/               崩溃、重复投递、备份恢复和一致性测试
evals/rag/                    脱敏评测样本、运行器与聚合报告
```

目录名称可在代码初始化时按实际工程结构微调，但职责不得合并到生产日志或在线实验系统。

## 5. 测试环境

### 5.1 环境分层

| 环境 | 用途 | 必需依赖 |
|---|---|---|
| 单元环境 | 快速回归 | 无外部网络；时间、随机数和 Provider 可控 |
| 集成环境 | 事务与协议验证 | 真实 PostgreSQL、pgvector、pg_trgm、Redis、MinIO；隔离的企业 PostgreSQL 测试库 |
| Compose 验收环境 | 发布拓扑验证 | 10 个长期服务、2 个一次性任务、固定镜像摘要和部署 Secret |
| 浏览器验收环境 | 用户路径验证 | Compose 对外 HTTPS 入口和企业实际部署使用的真实浏览器 |
| 恢复环境 | 空环境恢复演练 | 独立空数据卷、备份副本和相同发布版本 |

### 5.2 Provider 使用

- 单元和常规集成测试使用协议兼容的确定性替身，固定返回、延迟和错误序列。
- 发布前使用部署实际配置的 LLM、Embedding、Rerank、OCR/Vision Provider 做最小连通与格式验收。
- 真实 Provider 测试不发送生产文档、Secret 或未经批准的企业敏感评测语料。
- Provider 暂时不可用只说明该项阻塞或降级路径通过，不能据此判定完整 Agent/RAG 能力通过。

### 5.3 数据隔离

1. 每次测试运行使用独立数据库、Schema 或唯一命名空间。
2. 单元测试固定时钟、随机种子、ID 返回值和 Provider 响应。
3. 集成测试结束后只清理本次命名空间，不操作共享或生产数据。
4. 回收站 30 天、确认 900 秒和租约到期测试使用可控时钟，不通过真实长时间等待完成。
5. 并发测试使用屏障或明确调度点制造竞争，不能依赖偶然时序。
6. 测试失败时保留脱敏诊断信息；不保留 SQL、结果行、Chunk 正文、Memory 正文、模型参数全文或 Secret。

## 6. 标准测试数据

### 6.1 身份与权限数据

| 代号 | 数据 | 用途 |
|---|---|---|
| `U-ADMIN` | 全新系统初始化时创建的启用管理员 | 初始化幂等、登录、全局管理和管理员 Tool |
| `U-ADMIN2` | 第二个启用的管理员 | 多管理员并存和独立管理操作 |
| `U-A1` | 部门 A 普通用户 | 公共库、部门 A 库和本人资源 |
| `U-A2` | 部门 A 第二个普通用户 | 所有权隔离和并发 |
| `U-B1` | 部门 B 普通用户 | 部门隔离 |
| `U-DISABLED` | 部门 A 的停用普通用户 | 登录和现有令牌失效；历史会话与 Memory 保留 |

### 6.2 知识库与文件夹数据

- 一个公共知识库、部门 A 知识库和部门 B 知识库。
- 每库至少包含根级文件、空文件夹、非空文件夹、两层嵌套文件夹和同名但不同父级对象。
- 同一父级内准备名称冲突数据；不同父级准备允许同名数据。
- 准备在用、处理中、`partial_success`、失败、回收站和待永久清理对象。

### 6.3 文档语料

| 类型 | 最小样本 |
|---|---|
| PDF | 原生文本、扫描件、文本与图片混合、表格、损坏或加密文件 |
| DOC/DOCX | DOC 转换样本；DOCX 标题、段落、表格、图片、页眉页脚和精确字符定位样本 |
| PPT/PPTX | PPT 转换样本；PPTX 多 Slide、备注、图表、图片和表格 |
| XLS/XLSX/CSV | XLS 转换样本；XLSX 多 Sheet、合并单元格、公式结果、表格和空白区域；CSV 编码、分隔符和长字段样本 |
| Markdown/TXT | 中英文、代码块、长段落、编号和超长单元 |
| PNG/JPG/JPEG/WEBP | OCR 文本、图表、无可识别内容和超限图片，各扩展名至少一个有效样本 |
| 攻击样本 | 路径伪造、压缩炸弹特征、超时 Office 文件、提示注入文本和恶意元数据 |

至少准备两个内容相似但权限不同的文档、同一文档的新旧代次、精确型号/编号样本、同义改写样本和无依据问题。

### 6.4 企业 PostgreSQL 数据

- 两个允许的表、一个允许的 View、一个未授权表和一个未授权 Schema。
- 同名关系、主键、外键、可空字段、日期时间、数值、布尔、JSON 和大文本字段。
- 允许函数、非白名单函数、可能产生副作用的企业自定义函数和高消耗查询样本。
- Schema 新增、删除、改名和类型变化，用于快照漂移测试。
- 超过 100 行、序列化超过 1 MiB、超过 15 秒和可分页的稳定排序结果。

## 7. 通用通过规则

### 7.1 结果状态

每个用例只能记录以下状态之一：

| 状态 | 定义 |
|---|---|
| 通过 | 实际结果完全满足预期，证据完整 |
| 不通过 | 已执行但存在任一不满足项 |
| 阻塞 | 环境或外部依赖使步骤无法完成，未证明通过 |
| 未执行 | 未开始执行 |
| 不适用 | 经需求与测试负责人确认，该发布不包含此条件 |

### 7.2 严重级别

| 级别 | 判定示例 | 发布规则 |
|---|---|---|
| `P0` | 越权、企业数据库写入、旧代次泄漏、错误引用、Secret 泄漏、数据不可恢复 | 必须为 0 |
| `P1` | 核心闭环不可用、高风险绕过确认、任务不可恢复、关键格式完全不可处理 | 必须为 0 |
| `P2` | 有可接受替代路径的非核心缺陷、局部兼容或提示问题 | 必须有明确处置结论 |
| `P3` | 不影响正确性和安全性的轻微体验问题 | 可记录后处理 |

安全零容忍项即使只发生一次也按 `P0`，不能用平均成功率抵消。

### 7.3 用例最小字段

每个自动或人工用例至少记录：用例 ID、关联需求、前置条件、身份、输入、步骤、预期、实际、证据等级、结果状态、构建版本和执行时间。失败用例还需记录可复现条件，不记录受限正文或 Secret。

## 8. 静态与单元测试

### 8.1 静态准入

| 编号 | 检查项 | 通过条件 |
|---|---|---|
| `STA-001` | 后端格式、Lint 与类型 | 无阻断错误 |
| `STA-002` | 前端格式、Lint、类型与生产构建 | 无阻断错误且静态产物生成 |
| `STA-003` | Compose 配置展开 | 无未知键、空必填值、浮动镜像标签或未定义服务依赖 |
| `STA-004` | 数据库迁移链 | 可从空库顺序升级到目标版本，版本与应用声明一致 |
| `STA-005` | API、Tool 和错误码枚举 | 实现与已确认文档一致，无未设计入口 |
| `STA-006` | Secret 和受限内容扫描 | 仓库、镜像层、前端产物和默认配置无 Secret、SQL/结果样例和企业正文 |
| `STA-007` | 依赖与镜像漏洞 | 无未处理的高危或严重漏洞 |
| `STA-008` | 许可证检查 | `pglast` 等直接和传递依赖符合项目分发决策 |

### 8.2 必测纯规则

- 自增 `bigint` ID 的 API 表示为十进制字符串；非法、负数、越界和混合字符被拒绝。
- 名称按父级唯一；不同父级允许同名；大小写与规范化规则与数据库约束一致。
- 文件夹和文档只能在同一知识库内移动；跨库请求在任何写入前失败。
- 普通用户、管理员、公共库、部门库、本人资源和停用用户的权限矩阵逐格覆盖。
- 文档聚合状态、处理单元状态、Outbox 状态、Pending Action 状态和 Agent Run 状态只允许已定义转换。
- RRF、去重、相邻 Chunk 扩展、上下文预算、阈值和拒答规则使用固定输入输出验证。
- Tool Schema 拒绝未知字段，服务端身份、风险、权限和目标版本不能被模型参数覆盖。
- SQL AST、函数白名单、关系/字段解析、限制注入、分页和结果预算覆盖合法与恶意语料。
- 时间边界覆盖 900 秒确认有效期、30 天回收站、任务租约和缓存过期。

## 9. 数据库与事务验收

| 编号 | 场景 | 必须满足的结果 |
|---|---|---|
| `DB-001` | 空库执行完整迁移 | 所有 Schema、表、索引、约束和扩展成功建立 |
| `DB-002` | 重复执行初始化/迁移检查 | 不重复插入业务数据，不绕过版本控制 |
| `DB-003` | 同父级并发创建同名对象 | 只有一个事务成功，另一个返回名称冲突 |
| `DB-004` | 不同父级创建同名对象 | 均成功 |
| `DB-005` | 跨知识库移动文件夹或文档 | 事务拒绝且原对象位置不变 |
| `DB-006` | `row_version` 过期更新 | 返回并发冲突，不覆盖新值 |
| `DB-007` | 覆盖处理中读取文档 | 旧活跃代次继续检索和引用 |
| `DB-008` | 新代次完整成功 | 激活事务后立即只使用新代次，旧代次退出语义 |
| `DB-009` | 新代次失败 | 旧代次继续活跃，新失败代次可诊断和重试 |
| `DB-010` | 新代次满足可激活的 `partial_success` | 只激活已完整可检索单元；`pending`/失败单元不参与检索 |
| `DB-011` | 删除和恢复文件夹子树 | 同一删除批次正确覆盖子项；恢复不越过原知识库 |
| `DB-012` | 超过 30 天自动清理 | 只清理已到期且仍在回收站的数据及对象 |
| `DB-013` | Outbox 同一事件重复投递 | 最终只有一个有效业务结果 |
| `DB-014` | 两个 Worker 竞争同一处理单元 | 只有租约持有者提交有效结果 |
| `DB-015` | 会话物理删除 | 消息、Run、Tool 和回答来源级联删除；既有 Memory 保留且 `source_message_id` 置空；Checkpoint 最终清理 |
| `DB-016` | 删除被引用部门 | 有用户或知识库引用时拒绝；无引用时才允许 |
| `DB-017` | 管理员重置用户密码 | 锁定目标并校验 `row_version`；成功时密码哈希、`credential_version`、`row_version` 原子更新，失败时均不变 |

约束验收必须同时检查 API 错误和数据库最终状态，不能只断言 HTTP 状态码。

## 10. API 与实时协议验收

### 10.1 通用协议

| 编号 | 场景 | 必须满足的结果 |
|---|---|---|
| `API-001` | 登录成功与失败 | 成功返回令牌和用户摘要；错误凭据不泄漏用户是否存在 |
| `API-002` | 停用用户登录或使用旧令牌 | 请求被拒绝，不读取业务资源 |
| `API-003` | 非法 JSON、字段类型、未知字段 | 返回统一错误信封和稳定错误码 |
| `API-004` | 不存在与无权限资源 | 不通过差异响应泄漏资源存在性 |
| `API-005` | 同一 `Idempotency-Key` 重试 | 返回原结果，不重复创建资源、任务、Tool Call 或 Pending Action |
| `API-006` | 过期 `row_version` | 返回 `409` 类并发冲突，服务端状态不回退 |
| `API-007` | 错误响应与日志 | 不含堆栈、SQL、Secret、对象 Key、内部路径或企业正文 |
| `API-008` | 列表分页 | 顺序稳定、边界正确、无重复或遗漏，不提供未设计的全文搜索能力 |

| `ART-007` | 单文档总结、多文档总结对比和知识归纳 | 只使用授权来源，结论保留对应引用并说明来源不足 |
| `ART-008` | 中英互译、整篇或指定章节翻译、翻译后总结 | 范围和语言正确，译文及总结保留与原始来源的关系 |
| `ART-009` | 明确请求柱状图、折线图、饼图或表格 | 只生成请求类型，可导出 PNG/PDF/XLSX/CSV，并保留数据来源、统计口径和查询时间 |
| `ART-010` | 用户未明确要求图表 | 普通问答、分析或总结不自动生成图表文件 |

## 16. 真实浏览器验收

### 16.1 执行要求

1. 浏览器必须从 `https://<部署入口>/` 进入，只经 `reverse-proxy` 访问静态资源、API、SSE 和 WebSocket。
2. 使用发布构建，不用开发服务器或直接打开本地静态文件代替。
3. 每条用例同时检查页面结果、关键网络请求、浏览器控制台和最终数据库状态。
4. 浏览器截图只证明当时可见状态；涉及处理完成、权限和副作用时还需接口或数据库断言。
5. 使用企业实际部署使用的一个真实浏览器执行；浏览器版本和操作系统只作为本次证据环境记录，不据此新增浏览器兼容性范围。

### 16.2 核心浏览器路径

## 17. 安全验收

### 17.1 权限与资源枚举

- 对所有详情、列表、预览、下载、SSE、WebSocket、Pending Action、Run 和生成物接口执行横向越权测试。
- 普通用户伪造管理员路由、Tool 名、部门 ID、资源 ID 和 `actor_user_id` 均被服务端拒绝。
- 禁用用户、权限变更用户和部门变更用户的后续请求立即按当前权限判定。
- 错误码、响应时间和候选列表不泄漏未授权资源是否存在。

### 17.2 上传、解析与对象存储

- 校验扩展名、MIME、文件签名、大小、页数/单元数和解析预算，不信任客户端声明。
- 文件名、归档路径、对象 Key、系统路径和 URL 不能由模型或客户端越过服务端映射。
- Office 转换在无额外 capability、无 Provider/MCP 网络、受限时间和空间的容器内完成。
- MinIO Bucket 保持私有；签名地址短时有效，过期和权限撤销后不可继续使用。

### 17.3 提示注入与模型边界

- 文档正文、数据库注释、Tool 结果、OCR/Vision 文本和网页式标记一律作为不可信数据。
- 攻击文本不得修改系统指令、暴露未授权 Tool、提升风险等级权限或诱导直接执行 SQL。
- 模型输出不能作为鉴权、确认、SQL 安全或对象绑定的可信证据。
- 回答和流式事件不得暴露隐藏 Prompt、思维链、Secret 或内部异常。

### 17.4 网络、容器与供应链

- 宿主机只发布 443 和可选 80；所有内部服务端口不可从外部访问。
- `api`/`worker` 不直连企业 PostgreSQL，`database-mcp-server` 不访问 EnterpriseMind PostgreSQL、Redis 或 MinIO。
- 无服务使用 `privileged`、Docker Socket、宿主机根目录挂载或不必要 capability。
- 除 `api` / `worker` 到允许列表 Provider 外，其他公网出站均被拒绝；MCP 非登记企业数据库地址出站被拒绝。
- 发布镜像使用固定摘要；生产前完成漏洞与许可证扫描。
- MinIO 固定版本必须满足既定安全评审门槛，否则 V1 生产发布阻塞。

## 18. 故障、恢复与并发验收

| 编号 | 故障或竞争 | 必须满足的结果 |
|---|---|---|
| `REC-001` | API 在业务事务提交后、响应前崩溃 | 同一幂等键重试返回原结果，不重复创建 |
| `REC-002` | Worker 在外部调用成功后、结果提交前崩溃 | 恢复后幂等收敛，不产生两个活跃结果 |
| `REC-003` | Redis 清空并重启 | PostgreSQL Outbox/任务重建，业务事实不丢失 |
| `REC-004` | MinIO 暂时不可用 | 依赖操作安全失败；数据库不宣称对象 ready |
| `REC-005` | EnterpriseMind PostgreSQL 暂时不可用 | API Readiness 失败；恢复后事务状态一致 |
| `REC-006` | 企业 PostgreSQL 暂时不可用 | 基础页面保持可用；Database MCP 返回明确可恢复错误 |
| `REC-007` | Provider 超时、限流、临时 5xx | 只按既定分类最多重试 3 次并正确降级 |
| `REC-008` | Provider 鉴权或参数错误 | 不重试，不掩盖为网络错误 |
| `REC-009` | 两次接受同一确认并发到达 | 只有一次执行成功，另一请求返回既有终态 |
| `REC-010` | 确认期间对象或权限变化 | 绑定校验失败，无副作用 |
| `REC-011` | Agent Runner 崩溃后恢复 | 取得 Run 锁、读取 Checkpoint、重新鉴权并安全继续 |
| `REC-012` | 响应确认已提交但唤醒失败 | 恢复器补发同一 Pending Action 状态，不重复响应 |
| `REC-013` | Scheduler 多实例误启动 | 只有单活锁持有者执行周期任务 |
| `REC-014` | 删除与处理结果并发提交 | 删除状态胜出后不得重新激活对象 |
| `REC-015` | Schema 刷新与关系授权并发 | 授权按固定快照和 `row_version` 提交，不静默作用于漂移对象 |

故障注入后必须检查最终状态、重复对象、悬挂租约、未处理 Outbox、孤立 MinIO 对象和用户可见提示，不以“进程已恢复”作为唯一通过条件。

## 19. 性能与资源基准

需求未设置固定 SLA，因此 V1 不承诺固定响应时间或吞吐量。性能测试用于建立同硬件、同数据规模、同版本的可比较基线，并验证安全上限确实生效。

### 19.1 必须记录

- API、首个 SSE 事件、完整 Agent Run、上传到可检索、Schema 刷新和导出的 P50/P95。
- 关键词、查询 Embedding、向量、RRF、Rerank 和总检索 P50/P95。
- HNSW 扫描元组数、精确回退、候选数、最终 Chunk 数和上下文 Token 数。
- PostgreSQL 连接数、慢查询、CPU、内存和索引大小。
- Worker/Office 队列长度、租约恢复、单任务耗时和失败率。
- API、Worker、Office、MCP 的实际并发与容器重启次数。

只保存脱敏聚合值，不保存用户原始问题、SQL、查询结果、Chunk 正文、查询向量或 Memory 正文。

### 19.2 基准场景

| 编号 | 场景 | 通过条件 |
|---|---|---|
| `PERF-001` | API 2 Worker、处理 Worker 并发 2、Office 并发 1、MCP 并发 5 的既定资源配置 | 无越权、重复结果、死锁、OOM 或非预期重启 |
| `PERF-002` | 多用户同时保持 SSE/WebSocket 并执行普通查询 | 事件不串用户，最终状态可恢复，记录延迟基线 |
| `PERF-003` | 大文档与混合格式排队 | 并发槽生效，API 保持可用，资源不无界增长 |
| `PERF-004` | 超过 100 行、1 MiB、15 秒的数据库查询 | 分页、截断和超时硬上限准确生效 |
| `PERF-005` | HNSW 过滤后候选不足 | 达到既定召回门槛且不会无限迭代 |
| `PERF-006` | 同一硬件和数据集版本回归 | 与已批准基线比较并说明变化，不自行把记录值升级为 SLA |

## 20. Compose 与部署验收

### 20.1 启动和网络

| 编号 | 场景 | 必须满足的结果 |
|---|---|---|
| `DEP-001` | 全新环境启动 | PostgreSQL、Redis、MinIO 健康后，一次性任务成功，再启动应用和代理 |
| `DEP-002` | `migrate` 失败 | 非零退出，API/Worker 不绕过迁移启动 |
| `DEP-003` | `storage-init` 重复执行 | Bucket、账号和策略幂等，无额外公开 Bucket |
| `DEP-004` | 扫描 Compose 服务 | 恰好 10 个长期服务和 2 个一次性任务，无未设计服务 |
| `DEP-005` | 扫描宿主机监听端口 | 只有 443 和可选 80 |
| `DEP-006` | 访问静态资源、API、SSE 和 WebSocket | 全部只经 `reverse-proxy` |
| `DEP-007` | PostgreSQL/Redis/MinIO 未就绪 | 依赖服务 Readiness 不通过，不虚假宣称可用 |
| `DEP-008` | Provider 或企业数据库暂时不可用 | 不阻止基础 API 启动；对应业务能力显示准确状态 |
| `DEP-009` | 全新空系统及重复启动执行 `migrate` | 首次只从配置和密码 Secret 创建一个启用管理员；缺少必填值时失败；重复执行不新增、覆盖或重置账号，非空无管理员的异常库不自动提权 |

### 20.2 配置与 Secret

- 缺少必填 Secret、配置出现未知键或错误类型时，相关服务启动失败。
- 镜像、Compose 展开、`docker inspect`、前端产物、日志和错误响应均不含 Secret 值。
- Provider URL 和企业数据库目标必须符合允许列表；`secret_ref` 不能引用任意路径。
- Redis 不作为业务事实持久存储；持久卷仅用于 EnterpriseMind PostgreSQL 和 MinIO。
- 发布清单不得使用浮动镜像标签，实际部署摘要写入验收报告。

## 21. 备份与恢复验收

### 21.1 演练步骤

1. 在一致恢复点停止或冻结写入和后台领取。
2. 备份 EnterpriseMind PostgreSQL、MinIO 对象和必要部署配置；Redis 不纳入恢复备份。
3. 记录构建版本、迁移版本、镜像摘要、备份时间和对象清单。
4. 在独立空环境按既定顺序恢复 PostgreSQL 和 MinIO。
5. 启动相同发布版本，运行迁移与一致性检查。
6. 由 PostgreSQL 重建未完成任务和事件，不恢复 Redis 数据。
7. 执行下列业务验收并保存证据。

### 21.2 恢复通过条件

- 管理员和普通用户能够登录，角色、部门和知识库权限正确。
- 文件夹、文档、当前活跃代次、回收站和 30 天时间语义正确。
- 原文件、预览、派生对象、Chunk、Embedding 和来源锚点一致。
- 代表性问题可检索并点击引用定位。
- 未完成任务可恢复且不产生重复有效结果。
- 会话、消息、Agent Run、Tool、Pending Action 和 Checkpoint 满足既定保留与恢复规则。
- 单一 Database MCP 配置、active Schema 快照和关系授权一致；Secret 从部署 Secret 重新装载。
- 对象缺失、孤立对象或摘要不一致都会使恢复验收不通过，不能只记录告警后判定成功。

## 23. 回归策略

### 23.1 每次提交

- 运行受影响模块静态检查和单元测试。
- 修改权限、状态机、SQL Guard、名称或风险规则时，运行对应完整规则集。
- 修改迁移时，从空库执行迁移并运行数据库约束测试。
- 修改前端交互时，运行相关组件测试；核心路径变更还要运行对应浏览器用例。

### 23.2 阶段完整回归

- 阶段性实现完成后，在本地运行后端和前端完整静态检查、单元测试。
- PostgreSQL、Redis、MinIO 和 MCP 集成测试。
- 核心纵向闭环浏览器冒烟：登录 → 获得权限 → 上传 PDF/Markdown/TXT → 异步索引 → Agent 检索 → 有依据回答 → 引用定位。
- 所有零容忍权限、代次、引用和 SQL Guard 回归用例。

### 23.3 发布候选

- 完整 Compose、真实浏览器、完整 200 条 RAG 评测、Provider 最小真实连通、安全攻击语料、并发与故障恢复测试。
- 空环境安装、升级路径、备份恢复和回滚准备检查。
- 发布制品镜像摘要、迁移版本、配置摘要与测试报告一一对应。

## 24. 发布准入与完成定义

V1 发布候选必须同时满足：

1. 全部 `P0`、`P1` 缺陷为 0。
2. 所有权限、生命周期、引用和 Database MCP 零容忍指标无违规。
3. RAG 整体指标、关键切片和人工评测达到第 12 节门槛。
4. 核心 API、Compose 和真实浏览器纵向闭环全部通过。
5. 六类高风险操作、消歧、确认绑定、过期和并发用例全部通过。
6. SQL Guard 合法语料、攻击语料、真实只读账号和结果预算全部通过。
7. Redis 丢失、Worker 崩溃、确认恢复和覆盖失败的恢复路径全部通过。
8. 在独立空环境完成一次 PostgreSQL + MinIO 备份恢复并验证业务一致性。
9. 生产镜像无未处理高危或严重漏洞，Secret 与受限正文泄漏扫描为 0。
10. MinIO 维护风险和 `pglast` 许可证门槛均有明确的发布通过结论。

任何一项阻塞都不能标记为“已通过”。需求未定义固定 SLA，因此性能基准缺少固定延迟目标不会单独阻塞发布；但超时、行数、结果大小、资源隔离和无重复结果等已确认硬限制必须通过。

- SQL Guard 攻击语料汇总、企业只读账号校验和结果预算证据。
- 备份清单、恢复步骤、恢复后对象一致性和业务抽样结果。
- 未通过、阻塞和未执行项清单及发布处置结论。

证据包不得包含 Secret、访问令牌、密码、原始 SQL、数据库结果行、Chunk 正文、Memory 正文、完整 Prompt、查询向量或思维链。必要截图和响应必须先脱敏。

## 26. 已确认设计结论

1. V1 验收按 `E0` 至 `E5` 分级，真实浏览器、恢复和安全结论必须由对应等级证据支持。
2. 测试范围严格对应既有 V1 能力，不新增日志审计、独立搜索、仪表盘或其他排除项。
3. 权限泄漏、旧代次泄漏、跨代次错误引用、企业数据库写入和 Secret 泄漏均为零容忍。
4. 覆盖失败继续使用旧内容；只有新代次成功或满足既定可激活部分成功条件后，才以成功提交点切换语义。
5. 高风险严格限定为既有六类，消歧不能替代确认，确认必须重新鉴权并绑定目标版本。
6. Database MCP 必须通过应用 Guard、MCP 二次校验、企业只读账号和真实 PostgreSQL 执行四层验收。
7. 完整 RAG 评测沿用 200 条数据集、固定划分和既定数值门槛，不建立在线实验或 LLM-as-a-Judge。
8. 性能只建立目标硬件基线，不自行增加固定 SLA；已确认的资源和结果预算仍是硬门槛。
9. Redis 不纳入业务备份，恢复必须以 PostgreSQL 与 MinIO 的一致恢复点为基础重建未完成工作。
10. 只有 API、Compose、真实浏览器、安全、评测和恢复证据全部达到各自门槛，才能宣称 EnterpriseMind V1 完成验收。
